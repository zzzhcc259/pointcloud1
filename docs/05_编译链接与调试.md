# 05 编译、链接与调试

> [03](03_CMake入门.md) 和 [04](04_CMakeLists逐行解释.md) 讲的是"怎么把代码变成 exe"。
> 这份讲的是：**exe 出不来、或者出来了但行为不对，你怎么查。**

---

## 一、四个阶段，四类报错

你的代码要跑到屏幕上，必须闯过四关。**每一关的报错长得完全不一样**，
先判断在哪一关，比盲目搜索有效得多。

```
① 预处理 Preprocess      #include 展开、宏替换
       ↓ 失败 → error C1083（找不到头文件）
② 编译 Compile            每个 .cpp 独立变成 .obj
       ↓ 失败 → error C2065 / C3861 / C2664 / C1189 / C2027 ...
③ 链接 Link               所有 .obj + .lib 拼成 .exe
       ↓ 失败 → error LNK2019 / LNK2005 / LNK1169
④ 运行 Run                加载 .dll，执行
       ↓ 失败 → 无报错直接退出（退出码）/ 崩溃 / 结果不对
```

### 快速判断表

| 你看到 | 在哪一关 | 第一反应去看 |
|---|---|---|
| `fatal error C1083: 无法打开包括文件` | ① 预处理 | `target_include_directories`、`#include` 路径 |
| `error C2065: 未声明的标识符` | ② 编译 | 忘了 `#include`、拼错名字 |
| `error C3861: 找不到标识符` | ② 编译 | 函数没声明（`.h` 里没写，或没 include） |
| `error C2664: 无法将参数从...转换为...` | ② 编译 | 函数签名对不上 |
| `error C1189: #error : "..."` | ② 预处理 | 有人故意 `#error`，通常是环境/宏不对 |
| `error C2027: 使用了未定义类型` | ② 编译 | 只前置声明了 struct，没有完整定义 |
| `error LNK2019: 无法解析的外部符号` | ③ 链接 | **有声明没实现** / `.cpp` 没加进构建 / 命名空间不一致 |
| `error LNK2005: ... 已经在 xxx.obj 中定义` | ③ 链接 | **同一个函数定义了两遍** |
| `error LNK1169: 找到一个或多个多重定义的符号` | ③ 链接 | 通常和 LNK2005 一起出现 |
| 编译链接全过，运行立刻退出（`-1073741515`） | ④ 运行 | **缺 DLL** |
| 运行到某处崩溃（`0xC0000005`） | ④ 运行 | 空指针、野指针、越界 |
| 运行正常但结果不对 | ④ 运行 | 逻辑问题，**上调试器** |

## 二、编译阶段：读懂 `error C****`

### 例 1：`C2065` 未声明的标识符

**怎么制造**：在 `src\menu\menu_items.cpp` 里把 `#include "segmentation/ransac_plane.h"` 删掉。

**报错**：

```
error C2065: "RansacPlaneOptions": 未声明的标识符
```

**读法**：编译器在**这个文件里**没找到 `RansacPlaneOptions` 这个名字的定义。

**原因只有三种**：
1. 忘了 `#include`（最常见）
2. 名字拼错了（`RansacOptions` vs `RansacPlaneOptions`）
3. 它在命名空间里，你没写 `pcp::` 前缀，也没 `using namespace pcp;`

**注意**：报错行号可能指向**使用**它的地方，而不是问题源头。
所以看报错时**永远先看第一个**（通常最接近真正原因），后面几十条往往都是它连带的。

### 例 2：`C3861` 找不到标识符 —— 和 C2065 的区别

两者看起来一样，区别在：

- `C2065` 一般指**变量/类型**
- `C3861` 一般指**函数**

**怎么制造**：在 `src\core\console.h` 里删掉 `void printRule();` 这一行声明。

**报错**：

```
error C3861: "printRule": 找不到标识符
```

**为什么这个例子特别有教育意义**：`console.cpp` 里 `printRule()` 的实现**一个字都没动**，
它就在那里、编得挺好。但 `.h` 里没声明，别的文件就看不见它。

> **编译期只认声明。实现存在与否，编译器根本不检查。**

### 例 3：`C2664` 参数类型不匹配

**怎么制造**：把 `src\segmentation\ransac_plane.h` 里的

```cpp
AlgoResult runRansacPlane(const CloudPtr &cloud, const RansacPlaneOptions &opt);
```

改成

```cpp
AlgoResult runRansacPlane(CloudPtr cloud, const RansacPlaneOptions &opt);
```

（去掉了 `const &`）

**报错**：

```
error C2664: "pcp::AlgoResult pcp::runRansacPlane(pcp::CloudPtr,const pcp::RansacPlaneOptions &)":
无法将参数 1 从 "const pcp::CloudPtr" 转换为 "pcp::CloudPtr"
```

**读法**：调用方传的是 `const CloudPtr`（不能改的指针），
你要的是 `CloudPtr`（可改的），**C++ 不允许把"只读"的东西交给"可写"的接口**。

**这类错误的教训**：改函数签名时，`.h` 和 `.cpp` **必须同时改**，而且 `const`、`&`、`*`
一个都不能差。

### 例 4：`C1189` —— 有人故意让编译失败

本项目实际踩过的：

```
error C1189: #error: "Potential runtime error due to aligned malloc mismatch!"
```

**这不是 bug，这是保护。** PCL 的 `memory.h` 里写着：

```cpp
#if !defined(PCL_SILENCE_MALLOC_WARNING) && ...
#error "Potential runtime error due to aligned malloc mismatch! ..."
#endif
```

它检测到"你的代码编译选项和 PCL 库的编译选项不一致（AVX 对齐方式不同）"，
就故意让编译停下来 —— 否则你会得到一个"能编过但一跑就崩"的程序。

**本项目的 `C1189` 根因**：vcpkg 的另一套 PCL 混进来了。解决方法是
`CMakeLists.txt` 第 29 行的 `CMAKE_VS_GLOBALS`（见 [04](04_CMakeLists逐行解释.md) 第 4 段）。

**教训**：遇到 `C1189` 不要急着加 `#define PCL_SILENCE_MALLOC_WARNING=1` 把它静音。
**报错说"potential runtime error"，那就是真会错。** 先找为什么路径混了。

## 三、链接阶段：`LNK2019` 的三种根因

`LNK2019` 是初学者最常见的拦路虎。它只有一句话：**"有人要用，但没人实现"**。

但"没人实现"有三种可能，处理方法完全不同。

### 根因 A：实现文件没加进构建（最常见）

**怎么制造**：`CMakeLists.txt` 的 `target_sources` 里注释掉 `src/preprocessing/voxel_filter.cpp`。

**报错**：

```
error LNK2019: 无法解析的外部符号
"struct pcp::AlgoResult __cdecl pcp::runVoxelGrid(
    class std::shared_ptr<class pcl::PointCloud<struct pcp::PointT> const> const &,
    struct pcp::VoxelOptions const &)"
```

**怎么确认**：

```powershell
Select-String -Path E:\dianyunxulian\build\PointCloudPractice.vcxproj -Pattern "voxel_filter"
```

如果**搜不到**，就是这个问题。

**解决**：加回 `target_sources`，重新 configure。

### 根因 B：`.h` 里声明了，`.cpp` 里没实现

**怎么制造**：在 `src\preprocessing\voxel_filter.cpp` 里把 `runVoxelGrid` 的函数体整段删掉
（或者把函数改名成 `runVoxelGrid2`）。

**报错**：和上面一样。

**怎么区分 A 和 B**：
- A 是"文件根本没编"→ `.vcxproj` 里搜不到
- B 是"文件编了，但里面没这个函数"→ `.vcxproj` 里搜得到，但 `.obj` 里没这个符号

**解决 B**：把函数名改回来，或者把函数体补上。

### 根因 C：命名空间不一致

**怎么制造**：在 `src\preprocessing\voxel_filter.cpp` 里删掉文件末尾的 `}`（闭合 `namespace pcp` 的那个）。

**报错**（注意看找的名字）：

```
error LNK2019: 无法解析的外部符号 "struct pcp::AlgoResult __cdecl pcp::runVoxelGrid(...)"
```

**关键**：链接器在找 `pcp::runVoxelGrid`，而你的定义变成了全局的 `runVoxelGrid`。
**链接器只认完整名字（含命名空间）**，名字差一个字符都找不到。

**怎么快速发现**：在报错信息的 `无法解析的外部符号` 后面那串里，找 `::` 前面的部分。
如果那里有 `pcp::`，但你的 `.cpp` 里 `namespace pcp` 少了，就是这个问题。

### `LNK2005` 重复定义

**怎么制造**：把 `src\core\console.cpp` 里的 `printRule()` 实现复制一份到 `cloud_io.cpp` 末尾。

**报错**：

```
error LNK2005: "void __cdecl pcp::printRule(void)" (?printRule@pcp@@YAXXZ) 已经在 console.obj 中定义
error LNK1169: 找到一个或多个多重定义的符号
```

**规则**：**非 `inline` 函数的定义，在整个程序里只能出现一次。**

**什么时候会不小心犯**：
- 复制粘贴代码时带过去了
- 把函数体写在 `.h` 里但忘了 `inline`（`#pragma once` 只防同一文件重复包含，
  防不住多个 `.cpp` 各自包含一次）
- 全局变量定义在 `.h` 里（应该用 `inline` 或者 `extern` + `.cpp` 定义）

## 四、运行阶段：`-1073741515` 是什么

编译链接全过，双击 exe，窗口一闪就没了。在 PowerShell 里运行才能看到退出码：

```powershell
.\build\Release\PointCloudPractice.exe
$LASTEXITCODE
```

```
-1073741515
```

### 这个数字怎么读

它是 **32 位有符号数表示的 Windows 错误码**。转成十六进制：

```powershell
"{0:X8}" -f -1073741515
# 输出 C0000135
```

`0xC0000135` = `STATUS_DLL_NOT_FOUND` = **找不到 DLL**。

### 为什么"找不到 DLL"不打印任何错误

因为失败发生在**加载器阶段** —— 在你的 `main()` 还没开始执行之前。
程序当时只有一个入口地址，连 `std::cout` 都没初始化，所以没法打印任何东西。

### 怎么查是哪个 DLL 缺了

**办法 A（最快）**：

```powershell
. E:\PointCloudEnv\env.ps1
.\build\Release\PointCloudPractice.exe
```

如果这样就正常，那就是 PATH 里缺 PCL/VTK 的 `bin`。

**办法 B（看它到底依赖什么）**：

```powershell
# 列出 exe 依赖的 DLL（Windows 自带工具不一定有 dumpbin，试这个）
Get-ChildItem E:\dianyunxulian\build\Release -Filter *.dll | Measure-Object
```

如果 DLL 数量很少（只有几个），说明 POST_BUILD 的拷贝没生效。

**办法 C（用 VS 的依赖查看）**：
在 VS 里打开 `.sln`，用"调试 → 启动性能探查器"或者第三方工具 Dependencies.exe。
本项目没装这类工具，**办法 A 已经够用**。

### 本项目的情况

`CMakeLists.txt` 第 126~195 行的 POST_BUILD 会拷几十个 DLL 到 `build\Release\`。
所以**正常情况下直接运行就能跑**。

但实测中，**不激活 `env.ps1` 直接运行仍然失败**（退出码 -1073741515）——
说明 POST_BUILD 漏了某个 DLL（最可能是 VTK 的某个插件，或者 PCL 的间接依赖）。

**这不是本项目的 bug，这是 Windows 上搞 C++ 的常态。** PCL 依赖链非常深
（PCL → VTK → 系统库 → OpenNI2 → ...），靠手工凑齐所有 DLL 基本不可能。
**所以"先 `. env.ps1`"是标准做法**，而不是"配好了就不用设 PATH"。

## 五、调试：先学会打印，再学断点

### 阶段 1：`std::cout` 打印（本项目已经做了很多）

最简单的调试手段，而且在本项目里**已经在用**：

打开 `src\menu\algo_runner.cpp`，`runOnOriginalCloud()` 里打印了：

- 算法名
- 输入文件路径
- 输入点数
- 每个 metric
- 输出文件路径

**这本身就是调试信息。** 当结果不对时，先看这些数字：

| 数字异常 | 可能原因 |
|---|---|
| 输入点数 = 0 | PCD 没读到，或读到了错误的文件 |
| 输出点数 = 0 | 参数太严（体素太大、阈值太小） |
| 输出点数 = 输入点数 | 参数太松（等于没做滤波） |
| 平均点间距 = 0 或 inf | 点云只有 1 个点（除零） |

**打印调试的要点**：**一定要打印"中间量"，不只是最终结果。**
比如 RANSAC 里打印平面方程和法向量 —— 这一步让人一眼看出"找到的是平板还是管壁"（见 [12](12_RANSAC平面分割.md)）。

### 阶段 2：用 Visual Studio 的调试器

#### 准备

```powershell
start E:\dianyunxulian\build\PointCloudPractice.sln
```

工具栏确认：配置 = **Debug**，平台 = **x64**。

> 为什么必须 Debug：Release 下优化器会把变量"优化掉"，你看不到真实值，
> 断点位置也可能跳动。

#### 下断点

三种方式：
- 光标停在某行，按 **F9**
- 点行号左边的灰色竖条
- 右键 → 断点 → 插入断点

**本项目的建议断点位置**：

| 想查什么 | 在哪下断点 |
|---|---|
| PCD 读到了没有 | `src\core\cloud_io.cpp` 的 `loadCloud()` 中 `pcl::io::loadPCDFile` 那一行 |
| 点云是不是空的 | 同上，之后一行 |
| 算法参数对不对 | 各算法 `.cpp` 里 `AlgoResult runXxx(...)` 的第一行 |

#### 常用快捷键

| 键 | 名字 | 干什么 |
|---|---|---|
| **F5** | 开始调试 | 运行到第一个断点 |
| **F10** | 逐过程 | 执行一行，**遇到函数调用不进去** |

打开方式都在 **调试 → 窗口** 菜单里：

### 一个完整的调试实例：查"点云为什么是空的"

**场景**：你改了 `loadCloud` 的路径，程序跑起来说"读取失败"。

**步骤**：

1. 在 `src\core\cloud_io.cpp` 的 `loadCloud()` 第一行下断点（F9）
2. F5 启动，菜单里选 2（检查原始点云）
3. 程序停在断点。**局���变量**窗口里看 `absPath`：
   ```
   absPath: "E:/dianyunxulian/data/scene_original.pcd"
   ```
4. F10 逐过程往下走，走到 `pcl::io::loadPCDFile(...)` 之后

假设你只想在"点数超过 20000"时才停下来：

**什么时候用**：算法在循环里，你想看第 500 次迭代的状态。

## 六、崩溃排查：`0xC0000005`

这是**访问冲突（access violation）**，意思是"程序试图读写一块它不该碰的内存"。

```powershell
# 退出码的十六进制
"{0:X8}" -f -1073741819
# C0000005
```

### 三大常见原因

#### 原因 1：空指针解引用

```cpp
CloudPtr cloud;          // 默认是 nullptr
cloud->size();           // 💥 崩溃
```

**正确写法**（本项目到处在用）：

```cpp
if (!cloud || cloud->empty())
{
    printError("点云为空");
    return result;
}
```

打开 `src\menu\algo_runner.cpp` 看 `runOnOriginalCloud()`，两处都有这个检查。
**这不是啰嗦，这是防崩溃。**

#### 原因 2：索引越界

```cpp
for (int i = 0; i <= cloud->size(); ++i)   // ← 注意 <= 错了
    cloud->points[i];                       // 💥 最后一次越界
```

**C++ 不会替你检查越界。** 这是和"更安全的语言"最大的差别之一。

**排查**：在循环里加断言，或临时改成 `i < n` 并打印 `i`。

#### 原因 3：野指针 / 悬垂引用

```cpp
const CloudPtr &ref = makeTempCloud();   // 临时对象销毁了，ref 悬空
```

**本项目的常见场景**：lambda 捕获局部变量时用引用。

打开 `src\menu\menu_items.cpp`，你会看到：

```cpp
runOnOriginalCloud("欧氏聚类", [&opt](const CloudPtr &cloud) {
    return runEuclideanCluster(cloud, opt);
});
```

这里 `[&opt]` 捕获了局部变量 `opt` 的**引用**。
**安全吗？安全** —— 因为 `runOnOriginalCloud` 是**同步**调用，在它返回之前 `opt` 一直活着。
**如果** `runOnOriginalCloud` 把 lambda 存起来以后再调用，那就是悬垂引用、必崩。

**所以捕获引用时，一定要问："我返回之后，它还在吗？"**

### 崩溃时怎么定位到行

在 **Debug** 配置下，崩溃会直接停在出错那一行（VS 会弹出对话框，点"中断"）。
在 **Release** 下经常停在汇编或完全错误的地方，这就是为什么调试必须用 Debug。

**如果 Release 也崩、Debug 不崩**：典型的"未初始化变量"或"优化暴露的 UB"。
先把配置切到 Debug 复现，再逐步排查。

## 七、本项目的实测：验证"原始数据不会被写坏"

这一节记录一个**真正做过的验证**，因为它是一个值得学的调试思路。

### 需求

用户提出："这些算法都有可能会把原始数据删掉。"

### 代码怎么防

打开 `src\core\cloud_io.cpp` 的 `saveCloud()`，有一道硬保护：

```cpp
// 如果是"原始数据文件名"，除非显式允许，否则拒绝写入
if (!allowOriginal && fs::path(absPath).filename().string() == "scene_original.pcd")
{
    err = "拒绝写入 scene_original.pcd：原始数据只读，算法结果请写到 output/ 目录";
    return false;
}
```

它不依赖"调用方记得别写"，而是**在唯一的写入出口上拦住所有写操作**。

### 怎么验证它不是空话

1. 记下原始文件的哈希：
   ```powershell
   $before = (Get-FileHash E:\dianyunxulian\data\scene_original.pcd -Algorithm MD5).Hash
   ```
2. **临时**在 `src\menu\algo_runner.cpp` 里加一段，故意让算法去写原始文件：
   ```cpp
   std::string guardErr;
   const bool wrote = pcp::saveCloud(pcp::originalScenePath(), result.cloud, guardErr, false);
   pcp::printInfo(std::string("[回写防护测试] ") + (wrote ? "居然写成功了！" : "被拒绝：" + guardErr));
   ```
3. 重新编译，跑一次体素降采样，看输出：
   ```
   [信息] [回写防护测试] 被拒绝：拒绝写入 scene_original.pcd：原始数据只读，算法结果请写到 output/ 目录
   ```
4. 再算一次哈希，和 `$before` 比：
   ```powershell
   $after = (Get-FileHash E:\dianyunxulian\data\scene_original.pcd -Algorithm MD5).Hash
   $before -eq $after
   # True
   ```
5. **把那段临时验证代码删掉，重新编译。**

### 这个验证方法值得记住

**"我以为它有保护"和"我验证过它有保护"是两件事。**

验证的套路永远是三步：
1. **制造一个本该失败的操作**
2. **看它是不是真的失败了**
3. **确认副作用没发生**（用哈希、用文件大小、用时间戳）

## 九、几件"编译器不会告诉你，但你要知道"的事

### 1. 警告不要忽略

```powershell
cmake --build build --config Release 2>&1 | Select-String "warning"
```

本项目关掉了 `C4996`（弃用函数）和 `C4819`（非 ANSI 字符），
但**其它警告全部保留**。

**`warning C4244: "=": 从 "double" 到 "int" 的转换，可能丢失数据`** 这类警告，
在点云处理里非常常见（坐标是 `float`，参数是 `double`），而且**真的会丢精度**。

### 2. `float` 和 `double` 混用是点云里的经典坑

PCL 的 `PointXYZ` 坐标是 **`float`**（单精度，约 7 位有效数字）。
你的参数是 `double`。

```cpp
float x = 100000.1f;    // 存进去变成 100000.1015625
float y = x + 0.01f;    // 加了等于没加
```

**本项目的处理**：所有参数用 `double`（人输入的、打印的），
写入 `PointXYZ` 时才转 `float`（在 `generate_scene.cpp` 里）。

**后果**：如果坐标量级是 10 米（10000 mm），`float` 的精度约 0.001 mm，够用。
如果量级是 100 米，精度只剩 0.01 mm，对焊缝特征（要求 0.1 mm）就不够了。

### 3. `size()` 返回的是 `size_t`（无符号）

```cpp
for (int i = cloud->size() - 1; i >= 0; --i)   // 如果 size()==0，size()-1 变成巨大正数
```

**正确写法**：

```cpp
for (std::size_t i = cloud->size(); i-- > 0; )   // 或者用反向迭代器
```

### 4. PCL 的很多算法会往 `stderr` 打东西

比如：

```
[pcl::SampleConsensusModelPlane::isSampleGood] Sample points too similar or collinear!
```

**这些不是你的代码打印的**，是 PCL 内部 `PCL_WARN` 宏打的。
在 PowerShell 里它可能被显示成红色，看着像报错，其实只是警告。
**判断标准：看到 `[pcl::xxx]` 前缀的就是 PCL 的，不是你的 bug。**
