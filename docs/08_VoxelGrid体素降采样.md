# 08 VoxelGrid 体素降采样

> 对应代码：`src/preprocessing/voxel_filter.h`、`src/preprocessing/voxel_filter.cpp`
> 菜单入口：主菜单第 **3** 项
> 输出文件：`output/voxel_leaf<边长>.pcd`

---

## 1. 它解决什么问题

扫一次管道，得到 30 万个点。**问题是：这 30 万个点里有大量信息是重复的。**

管道表面在 2mm × 2mm 的一小块区域里有 3 个点 —— 这 3 个点的坐标差不到 1.5mm，
对你的几何分析几乎没有区别贡献，但会让：

- 算法变慢（欧氏聚类要对每个点查邻居，30 万点 × 每次查 30 个邻居）
- 内存变大
- 噪声的影响被放大（同一位置 3 个点各有各的噪声，算平均反而稳定；
  但如果你只挑一个用，就挑到了一个带噪声的值）

**体素降采样的思路**：**把空间切成小方块，每个方块里只留一个点（通常是方块内所有点的质心）。**

结果：点数大幅减少，**但形状基本不变**。

**它和"滤波"的区别（这是最关键的一句话）**：

| | 体素降采样 | 统计滤波 / 半径滤波 |
|---|---|---|
| 目的 | 让点**变少** | 让**坏点**消失 |
| 会不会删飞点 | **不会**（只是把飞点平均进体素） | 会 |
| 会不会改变密度 | 会（变成均匀） | 会（删掉稀疏处的点） |
| 点数 | 一定减少 | 一定减少 |
| **形态** | **保持** | **保持** |

**"点少了"和"坏点没了"是两件事。** 这是初学者最容易混的一点 ——
跑完体素降采样看见点数从 30251 变成 17847，就以为"点云被清理干净了"。

**没有。** 那 200 个飞点还在，只是它们现在各自变成了一个体素里的"质心"，
而且大概率还落在离管道很远的地方。

## 2. 直观几何解释：把空间切成豆腐块

想象你的点云泡在一个大豆腐里。你把豆腐切成 2mm × 2mm × 2mm 的小块：

```
     ┌──┬──┬──┬──┐
     │  │• │  │• │      每个小块里有 0~5 个点
     ├──┼──┼──┼──┤      • = 点
     │••│  │• │  │
     ├──┼──┼──┼──┤      规则：每个非空小块，只留一个点
     │  │• │••│  │            → 取这些点的"质心"
     └──┴──┴──┴──┘
              ↓
     ┌──┬──┬──┬──┐
     │  │◇ │  │◇ │      ◇ = 每个小块的质心
     ├──┼──┼──┼──┤      空的小块什么都不留
     │◇ │  │◇ │  │
     ├──┼──┼──┼──┤
     │  │◇ │◇ │  │
     └──┴──┴──┴──┘

     9 个点  →  5 个点
```

**坐标怎么算**：

设某个体素里有 $n$ 个点 $(x_1,y_1,z_1), \dots, (x_n,y_n,z_n)$，输出点就是它们的质心：

$$
\bar{x} = \frac{1}{n}\sum_{i=1}^{n} x_i, \qquad
\bar{y} = \frac{1}{n}\sum_{i=1}^{n} y_i, \qquad
\bar{z} = \frac{1}{n}\sum_{i=1}^{n} z_i
$$

**注意这不是"随便挑一个点"，是"取平均"。** 所以体素降采样**顺带有一点平滑作用**
（同一体素内的噪声互相抵消），但**它不是滤波器** —— 这一点在第 6 节会再强调。

## 3. 必要数学：输出点数怎么估

你可能想知道"设成 2.0 会剩多少点"。有个粗略估算：

**假设**：点云在某个面上是均匀的，平均点间距是 $d$，体素边长是 $\ell$。

**如果** $\ell \gg d$：每个体素覆盖的表面积是 $\ell^2$（近似当平面看），
里面平均有 $(\ell/d)^2$ 个点。所以：

$$
\text{输出点数} \approx \text{输入点数} \times \frac{d^2}{\ell^2}
= \frac{\text{输入点数}}{(\ell/d)^2}
$$

等价地：

$$
\text{保留比例} \approx \left(\frac{d}{\ell}\right)^2,
\qquad
\text{平均每体素点数} \approx \left(\frac{\ell}{d}\right)^2
$$

**用本项目的真实数字验算**：

- 输入 30251 点
- 平均点间距 $d = 1.470$ mm（菜单 2 测出来的）
- 体素边长 $\ell = 2.0$ mm

$$
\text{平均每体素点数} \approx \left(\frac{2.0}{1.470}\right)^2 = 1.85
$$

$$
\text{保留比例} \approx \left(\frac{1.470}{2.0}\right)^2 = 0.540
$$

**实测值**：

```
体素边长(mm)   : 2.000
输入点数       : 30251
输出点数       : 17847
保留比例       : 0.5900
平均每体素点数 : 1.695
```

**估算 1.85 vs 实测 1.695，误差 8%。估算 0.540 vs 实测 0.590。** 为什么有偏差？

因为**估算把圆柱面当成了平面**。实际上：

1. 圆柱是弯的，体素是方的。靠近体素边界时，一个 2mm 的方盒里装的曲面面积
   比 $2\times 2$ 大一点（曲面"斜着穿过"方盒，能装下更多面积）→ 每体素点数偏少
2. 管道有内外两层（外表面 + 内表面），轴向和环向的密度不同（1.5mm vs 1.309mm）
3. 平均点间距 1.470mm 是用 KD-Tree 最近邻估的，而最近邻距离在网格采样下
   **等于网格的最小步长**，不一定代表"平均"间距

**这 8% 的偏差不是 bug，是"用平面模型去估曲面"的固有误差。**

**这个估算式的真正用途**：给你一个**数量级直觉**。
如果实测保留比例和 $(\ell/d)^2$ 差了 3 倍以上，那就是有问题了。

## 5. 关键参数

`src/preprocessing/voxel_filter.h` 里的 `VoxelOptions`：

```cpp
struct VoxelOptions
{
    double leaf = 2.0;   // 体素边长（mm），X/Y/Z 三个方向用同一个值
};
```

| 参数 | 含义 | 默认值 | 合理范围（本场景） |
|---|---|---|---|
| `leaf` | 体素边长（三个方向相同） | 2.0 mm | 1.0 ~ 10.0 mm |

**只有这一个参数。** 这就是 VoxelGrid 最大的优点：**好调**。

**为什么默认是 2.0？**

- 点间距 1.470 mm
- `leaf = 2.0` 略大于点间距 → 每个体素平均 1.7 个点 → 点数减少到 59%
- 这是"降采样"的典型目标：**点少了，但形态还完全清楚**

**如果 `leaf < 点间距`（比如 1.0）**：每个体素最多一个点 → 点数**几乎不变**。
等于白跑一趟。代码里对此有提示（`voxel_filter.cpp:40-43`）：

```cpp
if (opt.leaf < 0.3)
{
    printWarn("体素边长小于 0.3mm，可能几乎不减少点数（每个体素本来就没几个点）");
}
```

**为什么阈值定 0.3 而不是 1.47？** 因为 0.3 是"明显没了"的保守界限，
而 1.0 ~ 1.47 之间效果本来就微妙，让用户自己去试更有教学价值。

## 6. 参数变大或变小会怎样

### `leaf` 变大（比如 2.0 → 5.0 → 10.0）

- ✅ 点数大幅减少，程序跑得更快
- ✅ 噪声被平均得更厉害（一个小体素里 20 个点的质心，噪声降到原来的 1/√20 ≈ 22%）
- ❌ **细节丢失**：坡口钝边只有 2mm 宽，`leaf = 5mm` 会让整个钝边压缩成一层点
- ❌ 薄壁管（本场景壁厚 12mm，但 `thin_pipe` 预设只有 6mm）可能被"压实"成一层面
- ❌ 两份点云之间的间隙（`rootGap = 3mm`）可能被"连起来"

**关键判断**：如果体素边长 > 你关心的最小几何特征尺寸，就不能用了。

本项目里：
- 坡口钝边宽度 `rootFace` 默认 2 mm
- 根部间隙 `rootGap` 默认 3 mm
- → **`leaf` 超过 2mm 就开始伤害坡口特征了**

### `leaf` 变小（比如 2.0 → 1.0 → 0.5）

- ✅ 形态更精细
- ❌ 点数几乎不减少（**降采样的意义就没了**）
- ❌ 算法速度和内存都没改善

### 一句话记忆

> **`leaf` 应该设在"点间距"和"最小特征尺寸"之间。**

本项目：$1.47 \text{ mm} < \text{leaf} < 2 \text{ mm}$。所以 2.0 已经是上限附近了。

## 7. 本项目的代码逐段解释

打开 `src/preprocessing/voxel_filter.cpp`（89 行）。

### 第 1 段：函数签名（19 行）

```cpp
AlgoResult runVoxelGrid(const CloudPtr &input, const VoxelOptions &opt)
```

- `const CloudPtr &input`：传的是**智能指针的引用**。
  加 `const` 表示"我不修改你给的指针指向"，加 `&` 表示"不拷贝指针"（省一次引用计数原子操作）。
- `const VoxelOptions &opt`：参数结构体，同理。
- 返回值 `AlgoResult`：统一的结果类型（定义在 `src/core/algo_result.h`）。
  里面有 `cloud`（主结果）、`rest`（剩余点，本算法不用）、`summary`（一句话说明）、
  `metrics`（数字指标）、`output_path`（存到哪了）。

**为什么所有算法都返回同一种类型？** 因为菜单里的 `runOnOriginalCloud()` 要统一处理它们：

```cpp
// src/menu/algo_runner.cpp
bool runOnOriginalCloud(const std::string &title, const AlgoFunc &algo);
```

如果每个算法各返回自己的结构，菜单就得写 7 份处理代码。

### 第 2 段：三重输入检查（26-43 行）

```cpp
if (!input || input->empty())
{
    result.summary = "输入点云为空，未执行";
    printError("输入点云为空");
    return result;
}
if (opt.leaf <= 0.0)
{
    result.summary = "体素边长为 0 或负数，未执行";
    printError("体素边长必须大于 0");
    return result;
}
if (opt.leaf < 0.3)
{
    printWarn("体素边长小于 0.3mm，可能几乎不减少点数（每个体素本来就没几个点）");
}
```

**为什么 `!input` 要单独判断？**

`CloudPtr` 是 `std::shared_ptr<CloudT>`。**默认构造的 shared_ptr 是空的（nullptr）**。
如果直接 `input->empty()`，空指针解引用 → 崩溃（`0xC0000005`）。

**`!input || input->empty()`** 这个写法利用了**短路求值**：

- `input` 为空 → `!input` 为 true → **后面的 `input->empty()` 根本不会执行** → 安全
- `input` 不为空 → 才会去调 `empty()`

**这是 C++ 里最重要的安全写法之一。**

**为什么 `leaf <= 0.0` 要报错而不是自动改成 1.0？**

因为**悄悄改用户的参数，会让人以为"我传 0 也能跑"**，
下次换个场景继续传 0，结果就不对了。**报错比纠正更有教育意义。**

**`leaf < 0.3` 为什么只警告不报错？**

因为 0.3 不是错的，只是"可能没用"。**警告的意思是"你可能不是这个意思"，不是"你错了"。**

### 第 3 段：组装 PCL 对象（48-52 行）

```cpp
pcl::VoxelGrid<PointT> voxel;
voxel.setInputCloud(input);

const float leaf = static_cast<float>(opt.leaf);
voxel.setLeafSize(leaf, leaf, leaf);
```

**`pcl::VoxelGrid<PointT>`** 是个**模板类**。尖括号里写点类型。

`PointT` 是 `pcl::PointXYZ` 的别名（`src/core/types.h:27`）。**为什么用别名？**

如果将来要换成带反射强度的 `pcl::PointXYZI`（真实线激光传感器会输出强度），
只需改 `types.h` 一行：

```cpp
using PointT = pcl::PointXYZI;   // 从 PointXYZ 改成这里
```

**全项目 20 个 .cpp 一个字都不用改。** 这是"留后路"设计。

**`static_cast<float>(opt.leaf)` 为什么需要？**

`opt.leaf` 是 `double`，`setLeafSize` 要 `float`。
C++ 会**隐式转换**（不报错），但会触发警告 `C4244: 从 "double" 到 "float" 转换可能丢数据`。

本项目编译选项里有 `/wd4996`（关掉某些警告）但**没有关 C4244**。
所以加了显式 `static_cast` 来表明"我知道有精度损失，故意的"。

**注意**：`setLeafSize` 接受三个参数，本项目三个方向用同一个值。
**它完全可以不同** —— 比如"沿轴向 2mm、环向 1mm"，用于"轴向降采样得更狠"。
本项目没用这个能力，但你要知道它有。

### 第 4 段：执行（56-57 行）

```cpp
CloudPtr output(new CloudT);
voxel.filter(*output);
```

**这是 PCL 里最容易被坑的一行。**

`filter(PointCloud &output)` 的**参数是引用，不是返回值**。
它**不会帮你 new 一个新的点云**，而是往你给的容器里填。

**如果你写**：

```cpp
CloudT *output = nullptr;
voxel.filter(*output);   // 崩溃！解引用空指针
```

或者：

```cpp
CloudPtr output;          // 空的 shared_ptr
voxel.filter(*output);    // 崩溃！
```

**必须自己分配**：`CloudPtr output(new CloudT);`（或者 `std::make_shared<CloudT>()`）。

**为什么不用 `make_shared`？** 两者等价，`new` 只是更直白地表达"这里分配了内存"。
本项目统一用 `new`。

**`*output`** 是"解引用智能指针，得到它指向的对象"，传的其实是 `CloudT&`。

### 第 5 段：修 `is_dense`（61 行）

```cpp
output->is_dense = input->is_dense;
```

**`is_dense` 是什么？** PCL 的一个标记位：`true` = 所有点都是有限值（没有 NaN/Inf），
`false` = 可能有无效点。

**为什么要手动设置？** 因为 `filter()` 生成的新点云，`is_dense` 的默认值是 `true`
（`PointCloud` 构造函数里设的）。如果输入点云本来是 `false`（有 NaN），
输出就会**错误地声称自己是干净的**，导致后续算法跳过 NaN 检查。

**这是 PCL 的一个历史遗留小坑。** 本项目输入都是干净的（`is_dense = true`），
所以这行不影响结果，但写上它是对的。

### 第 6 段：算指标（64-72 行）

```cpp
const double n_in  = static_cast<double>(input->size());
const double n_out = static_cast<double>(output->size());

result.metrics["体素边长(mm)"]   = opt.leaf;
result.metrics["输入点数"]       = n_in;
result.metrics["输出点数"]       = n_out;
result.metrics["保留比例"]       = (n_in > 0.0) ? n_out / n_in : 0.0;
result.metrics["平均每体素点数"] = (n_out > 0.0) ? n_in / n_out : 0.0;
```

**`static_cast<double>(size_t)` 为什么必要？**

`input->size()` 返回 `size_t`（无符号整数）。如果直接 `n_out / n_in` 两个 `size_t` 相除，
会做**整数除法**：`17847 / 30251 = 0`，不是 0.59。

**这个错误非常隐蔽**：程序不报错，只是保留比例永远显示 0。

**转成 `double` 才是有小数点的除法。**

**`(n_in > 0.0) ? ... : 0.0` 为什么？**

防止除零。虽然前面已经检查过 `input->empty()`（所以 `n_in > 0` 必然成立），
但**防御性编程**：以后如果检查逻辑被改了，这里也不会崩。

**`result.metrics` 是 `std::map<std::string, double>`。**

键用**中文**是故意的 —— 打印时直接就是给人看的。代价是打印时还要
`displayWidth()` 算中文宽度才能对齐（见 `src/core/console.cpp`）。

### 第 7 段：生成输出文件名（76-78 行）

```cpp
std::ostringstream tag;
tag << "leaf" << std::fixed << std::setprecision(3) << opt.leaf;
result.output_path = saveOutput("voxel", tag.str(), output);
```

**为什么文件名里要带参数？**

如果你**不带参数**：

```
output/voxel.pcd     ← 第一次跑（leaf=2.0）写这个
output/voxel.pcd     ← 第二次跑（leaf=5.0）覆盖了！
```

**结果**：你想对比 2.0 和 5.0 的效果，但第一个文件已经没了。

**带上参数**：

```
output/voxel_leaf2.000.pcd
output/voxel_leaf5.000.pcd     ← 两个都在，能对比
```

**`std::fixed << std::setprecision(3)`** 把 2.0 格式化成 `"2.000"`。
为什么统一 3 位小数？因为不同 `leaf` 值格式化出来的长度不同
（`2.0` → `"2"`，`1.25` → `"1.25"`），文件名长短不一不好看也不易排序。
**固定 3 位后，字典序 = 数值序。**

**`saveOutput` 干了什么？**（`src/core/cloud_io.cpp`）

1. 拼出 `output/voxel_leaf2.000.pcd` 的绝对路径
2. 确保 `output/` 目录存在（不存在就创建）
3. 调 `saveCloud()` 写文件

### 第 8 段：收尾（80-86 行）

```cpp
if (result.output_path.empty())
{
    printError("结果保存失败（详见上面的提示）");
}

result.summary = "体素降采样完成";
return result;
```

**`result.output_path.empty()` 表示保存失败**（`saveOutput` 失败时返回空字符串）。

**注意这里没有 `return`** —— 因为即使保存失败，`result.cloud` 里还是有正确的点云数据，
菜单可以继续打印点数等信息。**"结果存不下来"和"算法没跑"是两件事。**

## 9. 怎么检查结果是否合理

**四条检查，按顺序做。**

### 检查 1：点数的数量级对不对

用第 3 节的估算式：$(\ell/d)^2 = (2.0/1.47)^2 = 1.85$。

实测 1.695 —— **在 10% 以内，合理**。

**如果实测是 0.3 或 10**，说明有问题：
- 0.3 → 体素比点间距小太多
- 10 → 点云本身有问题（比如点集中在很小的区域）

### 检查 2：点间距应该变大

**降采样后点间距应该接近体素边长。**

原因：每个体素留一个点 → 相邻非空体素的距离 ≈ 体素边长。

**怎么测？** 用菜单 2（检查原始点云）不行（那个固定读原始文件）。
**用 KD-Tree 的 KNN（菜单 6），查询某个点，k=8，看最近距离。**

原始点云：最近 1.46 mm。
降采样后（`leaf=2.0`）：应该变成 **约 2.0 mm 量级**。

**如果降采样后最近距离还是 1.46mm**，说明文件存错了（存成了原始点云）。

### 检查 3：形态没变

这是最重要的检查，但**用数字不好查，用可视化最直接**。

**看坐标范围**：

原始点云 X 范围 `[-179.476, 169.643]`（这被飞点撑大了）。

**降采样后的坐标范围几乎不变** —— 因为质心一定在原点的凸包内。

**如果坐标范围明显缩小了**（比如少了一半），说明 `leaf` 太大，
把整个物体"压实"了。

**真要确认形态，用 CloudCompare 叠加对比**（见 [15_可视化用法.md](15_可视化用法.md)）。

### 检查 4：飞点还在不在

**跑完体素降采样，`output/voxel_leaf2.000.pcd` 里还有离群点。**

**怎么验证？** 打开菜单 4（SOR），看它删掉多少个点。

- 原始点云 → SOR 删 196 个
- 体素降采样结果 → SOR 应该删**接近 200 个**（因为飞点变成了独立的体素质心，
  一个飞点一个体素，所以数量几乎不变）

**如果 SOR 删掉 0 个**，说明飞点真的没了（那才是奇怪的）。

**这个检查的目的是让你亲眼确认"体素降采样不是滤波器"。**

## 11. 常见报错

### `error C2039: "VoxelGrid": 不是 "pcl" 的成员`

**原因**：忘了 `#include <pcl/filters/voxel_grid.h>`。

**注意**：PCL 的头文件路径**极其具体**。不是 `<pcl/voxel_grid.h>`，
不是 `<pcl/filters.h>`，而是 `<pcl/filters/voxel_grid.h>`。

### `error LNK2019: 无法解析的外部符号 ... pcl::VoxelGrid...`

**原因**：`find_package` 里没写 `filters` 组件。

检查 `CMakeLists.txt` 第 42-51 行的组件列表：

```cmake
find_package(PCL 1.15 REQUIRED COMPONENTS
    common io filters features search kdtree segmentation visualization)
                ↑ 这个
```

### `filter()` 调用后程序崩溃（无提示退出）

**原因**：`output` 是空的智能指针。

**错**：

```cpp
CloudPtr output;
voxel.filter(*output);     // 崩溃
```

**对**：

```cpp
CloudPtr output(new CloudT);
voxel.filter(*output);
```

### 输出点数和输入一样（或者只少几个）

**三个可能**：

1. `leaf` 设得太小（小于点间距）→ 这是"预期行为"，见第 6 节
2. `setLeafSize` 没被调用（检查代码是否漏了这行）
3. 读的是错的文件（检查打印的"读入原始点云"路径）

### 保留比例打印成 `0`（而不是 0.59）

**原因**：整数除法。见第 7 节第 6 段。

### 中文输出乱码

**原因**：控制台代码页不是 UTF-8。

**本项目已经在 `main()` 里调了 `setupConsole()`**（`src/core/console.cpp`），
它调用 Win32 的 `SetConsoleOutputCP(CP_UTF8)`。如果还乱码，
检查是不是在别的终端里跑的（比如某些 IDE 的内置终端）。

## 12. 与管道焊缝点云处理的联系

### 联系 1：这是焊缝点云处理的第一步

几乎所有焊缝点云论文的流程都是：

```
线激光扫描 → 点云去噪 → 降采样 → 分割焊缝区域 → 提取特征 → 规划路径
                          ↑
                      VoxelGrid 在这里
```

**为什么必须先降采样？** 因为后续的"法向估计""曲率计算""聚类"都是
**O(n log n) 到 O(n²)** 的操作，30 万点根本跑不动。

### 联系 2：体素大小要和焊缝尺寸匹配

**管道的环焊缝**：坡口宽度通常 10~20mm，钝边 1~3mm，根部间隙 2~4mm。

**体素边长必须小于你关心的最小尺寸。** 若 `leaf = 5mm`：

- 钝边（2mm）→ 被压成一层面
- 根部间隙（3mm）→ 可能被"填平"
- **张口宽度 b 就量不准了**

**工业做法**：焊缝特征提取时常用 `leaf = 1~2mm`，
而"只需要看整体形状"时用 `leaf = 5~10mm`。

### 联系 3（本项目最重要的）：**降采样会改变 b 和 h 的测量值**

张口宽度 $b$ 是坡口两侧边缘的距离。降采样后：

- 边缘点变成了体素质心 → 边缘位置有**半个体素**的偏移
- 坡口斜面上的点被稀疏化 → 边缘检测（法向突变）可能失效

**所以正确顺序是**：

```
原始点云 → 先算 b 和 h（在原始密度上）→ 再降采样做后续处理
```

**而不是**：

```
原始点云 → 降采样 → 算 b 和 h      ← b 会偏大或偏小，且不可预测
```

**这是本项目 `docs/01` 里强调"统一测试场景"的原因之一**：
让你能在同一份数据上对比"先降采样"和"后降采样"的差别。

### 联系 4：真实扫描数据里密度不均匀（本项目没有的问题）

**本项目的合成点云密度是均匀的**（环向 1.309mm、轴向 1.5mm 处处一样）。

**真实线激光扫描**：

- 正对激光的点密（可能 0.5mm）
- 斜着的点稀（可能 3mm，因为入射角大导致投影拉长）
- 有遮挡的地方直接没点

**后果**：`leaf = 2.0` 在密集区留下 10 个点、在稀疏区留下 0 个点。
**降采样放大了不均匀性。**

**真实数据的应对**：用**自适应体素**（按局部密度调 `leaf`），或者先做
"密度归一化"再降采样。本项目没做，因为合成数据不需要。

## 13. 算法在真实扫描数据中的局限

| 局限 | 说明 | 本项目是否遇到 |
|---|---|---|
| **薄壁被压穿** | 壁厚小于 `leaf` 时，内外表面合成一层 | 不遇到（壁厚 12mm，`thin_pipe` 也有 6mm） |
| **间隙被填平** | 两个物体间距小于 `leaf` 时，质心可能"桥接" | 不遇到（间隙 3mm，`leaf=2.0` 时勉强安全） |
| **边缘偏移半个体素** | 边缘点的位置有系统偏差 | 不遇到（但做特征提取时要注意） |
| **密度不均匀时失效** | 密集区降得少、稀疏区降得多 | 不遇到（合成数据均匀） |
| **不是滤波器** | 飞点还在 | **会遇到**（200 个飞点依然存在） |
| **不支持法向/颜色** | 质心会"平均掉"法向和颜色 | 不遇到（`PointXYZ` 只有坐标） |
| **只支持正方体体素** | 不能"轴向 5mm、环向 1mm" | 不遇到（但 API 支持三个不同值） |
