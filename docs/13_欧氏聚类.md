## 一、这个算法解决什么问题

一句话：**把"挨在一起"的点分成一堆一堆，每堆算一个物体。**

前两个分割思路是：

- **PassThrough**（[11](11_PassThrough坐标裁剪.md)）：按**坐标**硬切 —— 你得先知道东西在哪
- **RANSAC**（[12](12_RANSAC平面分割.md)）：按**几何形状**找 —— 你得知道要找什么形状

**欧氏聚类不需要你知道任何东西。** 它只问一个问题：

> **这两个点是不是离得很近？挨着的算一伙，不挨着的算两伙。**

### 本项目场景里的效果

场景里有三样东西：一根管道（25920 点）、一块平板（4131 点）、200 个飞点。

**用容差 3.0 mm 跑一次 → 得到 2 簇**：

| 序号 | 点数 | 重心 | 是什么 |
|---|---|---|---|
| 1 | 25921 | `(0.00, 0.00, 0.00)` | 管道（+1 个粘上的飞点） |
| 2 | 4131 | `(-0.00, 200.00, 0.00)` | 平板（y=200） |

**注意"2 簇"这个结果本身就是一个重要发现**：

- 200 个飞点**没有**形成簇 —— 因为它们彼此离得远（撒在 ±180 的空间里），
  而且每个飞点周围 3 mm 内没有别的点
- 所以它们被 `minSize = 50` 过滤掉了

**这就是欧氏聚类和 RANSAC 的根本差别**：
RANSAC 会说"这 200 个飞点里，某 3 个凑巧能定一个平面"；
欧氏聚类会说"这 200 个点每个都是孤立的，全丢掉"。

## 二、直观几何解释

### 一维的"分堆"

```
    数字轴上有一串点：
    ● ● ● ●        ● ●        ● ● ● ● ●
    └─一堆─┘      └一堆┘      └──一堆──┘

    只要相邻两点距离 < 容差，就算同一堆
```

**就这么朴素。** 没有形状、没有模型、没有拟合。

### 二维的"分堆"：关键是"传递"

```
    ● ● ● ● ● ● ● ● ● ● ●
```

这一串点，相邻间距都是 0.5。容差设 1.0。

**问题**：第 1 个点和第 10 个点距离 4.5，**远大于容差 1.0**。
它们算一堆吗？

**答案：算。**

因为 1↔2 连通，2↔3 连通，... 9↔10 连通。
**连通关系是传递的** —— 这就是"聚类"和"最近邻"的根本区别。

```
    ●─●─●─●─●─●─●─●─●─●
     连通关系像一条链子
     → 整条链子是一簇，哪怕两头离得远
```

**这个性质很重要，也是坑**：

> 如果两个物体之间**有一条细线状的点相连**（比如焊渣、飞边、扫描时的条纹），
> 它们就会被连成**同一簇**，哪怕你觉得它们明明是两个东西。

### 算法怎么做的：从种子点开始"蔓延"

```
1. 随便找一个还没被访问过的点，当作种子
2. 找出它周围容差内的所有点，加入当前簇
3. 对每个新加入的点，再找它周围容差内的点...
4. 直到没有新点可以加入 → 这一簇结束
5. 回到第 1 步，找下一个没访问过的点
```

**这就是"广度优先搜索"（BFS）**，或者叫"洪水填充"（flood fill）。

**用一幅图理解**：

```
    ╭──────────────────────────────────╮
    │  未访问的点                       │
    │      ● ● ●                       │
    │   ● ● ● ● ● ● ← 第 1 步：选种子     │
    │      ● ● ●                       │
    │                                  │
    │  第 2 步：种子周围 3mm 内的都进来  │
    │  第 3 步：新进来的点，再看它们周围  │
    │  ...                              │
    │  第 N 步：没有新点 → 这簇结束      │
    ╰──────────────────────────────────╯
```

### 为什么它依赖 KD-Tree

第 2 步和第 3 步都是"找周围容差内的点" —— 这就是**半径搜索**。

如果对每个点都**遍历全部 30251 个点**算距离：
$$30251 \times 30251 \approx 9.15 \times 10^8 \text{ 次距离计算}$$

每次距离计算要 3 次减法、3 次乘法、2 次加法 —— 约 **90 亿次浮点运算**。

**用 KD-Tree**：每次搜索只访问 O(log n) ~ O(k) 个节点，
总复杂度降到 $O(n \log n)$，**快几个数量级**。

**所以代码第 48–49 行必须先建树**：

```cpp
pcl::search::KdTree<PointT>::Ptr tree(new pcl::search::KdTree<PointT>);
tree->setInputCloud(input);
```

**这是 [10_KDTree邻域搜索](10_KDTree邻域搜索.md) 的直接应用** ——
KD-Tree 本身不是算法，它是很多算法（包括聚类）的**底层零件**。

## 三、数学原理

### 3.1 距离

用的是**欧氏距离**（这就是"欧氏聚类"名字的由来）：

$$d(p, q) = \sqrt{(x_p-x_q)^2 + (y_p-y_q)^2 + (z_p-z_q)^2}$$

**注意**：实际实现里通常比较**平方距离**（省掉开方）：

$$d^2(p,q) < \epsilon^2 \iff d(p,q) < \epsilon$$

因为开方是单调的，不影响比较结果。**这是一条常见的性能优化。**

### 3.2 连通性的形式化

定义一个图 $G = (V, E)$：

- 顶点 $V$ = 所有点
- 边 $E$ = 所有满足 $d(p_i, p_j) < \epsilon$ 的点对

**聚类 = 求这个图的连通分量**（connected components）。

$\epsilon$ 就是 `clusterTolerance`。

### 3.3 复杂度

| 阶段 | 复杂度 | 本项目 30251 点 |
|---|---|---|
| 建 KD-Tree | $O(n \log n)$ | 毫秒级 |
| 每点半径搜索 | $O(\log n + k)$，$k$ 是邻居数 | |
| 全部搜索 | $O(n \log n + nk)$ | 实测几十毫秒 |
| 总 | $O(n \log n)$ 量级 | |

**注意 $k$ 的影响**：如果容差设得很大，每个点的邻居数 $k$ 会很大，
复杂度退化成接近 $O(n^2)$。**所以容差不能乱设大。**

### 3.4 容差该设多少

**核心原则：容差必须大于"最稀疏方向上的点间距"。**

本项目管道是**网格采样**：

- 周向：`ntheta = 240` 圈，半径 50 → 间距 $2\pi \times 50 / 240 = 1.309$ mm
- 轴向：`axialStep = 1.5` mm

**最远的"最近邻"是斜对角**：

$$\sqrt{1.309^2 + 1.5^2} = \sqrt{1.713 + 2.25} = \sqrt{3.963} \approx 1.991 \text{ mm}$$

**并且**：因为加了 `noiseSigma = 0.05` mm 的噪声，实际距离会在 1.991 附近波动 ±0.07。

**所以容差必须 > 2.06 左右才安全。** 取 3.0（1.5 倍余量）是合理的。

## 五、关键参数

### `clusterTolerance` —— 聚类容差（mm）

**最重要的参数。** 决定"多近算挨着"。

**太小** → 点之间连不上 → 每个点都是独立的一簇（或者全被 `minSize` 过滤掉）

**太大** → 不同物体连成一簇 → 分不开

**经验值**：**1.5 ~ 3 倍平均点间距**。

本项目平均点间距 1.470 mm（菜单 2 可看），但**局部最远最近邻是 1.991 mm**。
所以：

| 容差 | 相当于 | 效果 |
|---|---|---|
| 1.0 | 0.5 倍 | **完全失效**（0 簇） |
| 2.0 | 1.0 倍 | **管道被切碎**（20 簇） |
| **3.0** | **1.5 倍** | **正确（2 簇）** |
| 5.0 | 2.5 倍 | 正确，但开始吸入飞点 |
| 10.0 | 5 倍 | 正确，吸入更多飞点 |

### `minSize` —— 最小簇点数

**小于这个数的簇直接丢掉。**

**作用**：**过滤噪点和碎片**。

- 设 50 → 200 个飞点全部被丢掉（它们各自成不了 50 点的簇）
- 设 1 → 飞点会全部作为"小簇"出现，输出几百簇
- 设 30000 → **一个簇都不剩**（最大的管道才 25921）

**设多少合适？** 取决于"你关心的物体最小有多少点"。

如果关心的是一个直径 3 mm 的小焊缝缺陷，那 `minSize` 就得很小。

### `maxSize` —— 最大簇点数

**大于这个数的簇直接丢掉。**

**作用**：过滤"大得不像目标"的东西。

**什么时候用**：当你只想找**零件**，不想找**工作台**。工作台往往连成一片巨大的簇。

本项目默认 `1000000`（等于不限制）。

## 六、参数变大变小的效果（实测）

全部实测，场景 = 默认 `pipe_plate`，30251 点，`minSize = 50`：

| 容差 | 簇数 | 最大簇点数 | 最大簇占比 | 结果解读 |
|---|---|---|---|---|
| **1.0** | **0** | — | — | **完全失效** |
| **2.0** | **20** | **12960** | 0.4284 | **管道被切成好几块** |
| **3.0** | **2** | **25921** | 0.8569 | ✅ 正确 |
| 5.0 | 2 | 25923 | 0.8569 | 正确，多吸 2 个飞点 |
| 10.0 | 2 | 25925 | 0.8570 | 多吸 4 个飞点 |

### 为什么容差 1.0 完全失效

因为**所有相邻点间距都 > 1.0**：

- 周向 1.309 > 1.0
- 轴向 1.5 > 1.0

所以**没有任何两个点相连**。30251 个点，30251 个独立簇，每个 1 点，
全部被 `minSize = 50` 过滤 → **0 簇**。

**这是最典型的"参数太小"的后果**：不是报错，是**静默地返回空**。

### 为什么容差 2.0 会把管道切碎（这个案例很珍贵）

斜对角距离是 1.991，**理论上传 2.0 应该够**。但实测切成了 20 块，最大簇只有 12960。

**原因是噪声。**

我们的点加了 `noiseSigma = 0.05` mm 的三维高斯噪声。
两个点的距离因此会波动：

$$d_{实际} \approx d_{理想} \pm \sqrt{2} \times \sigma \approx 1.991 \pm 0.07$$

**也就是说，真实距离可能到 2.06，超过了 2.0。**

于是**一部分斜对角连接断了**，连通图碎裂。

**这个案例教的东西**：

> **容差不能"刚好等于"理论点间距，必须留 1.5 倍以上的余量。**
> 因为真实点云永远有噪声，噪声会把"刚好够"变成"不够"。

而且注意：**剩余的那些连接（轴向 1.5、周向 1.309）还在**，
所以管道不是碎成 30251 块，而是碎成 20 块 —— 每块内部靠 1.5 和 1.309 连通，
块与块之间靠斜对角连通 —— **斜对角一断，就切开。**

### 为什么容差越来越大时最大簇点数会缓慢上升

| 容差 | 最大簇 | 差值 |
|---|---|---|
| 3.0 | 25921 | 基线 |
| 5.0 | 25923 | +2 |
| 10.0 | 25925 | +4 |

**多出来的是飞点。**

管道 25920 点，容差 3.0 时有 **1 个**飞点恰好落在管道某个点 3 mm 内，
被吸进管道这一簇。容差 10.0 时有 **5 个**。

**这告诉我们一件事**：**欧氏聚类不能去噪，它会"粘住"噪声。**

一个孤立的飞点本身成不了 50 点的簇（会被 `minSize` 滤掉），
但如果它**挨着真物体**，就会被吸进那个簇。

**所以正确顺序是**：先 SOR 去噪，再聚类。

## 七、代码逐段解释

打开 [`src/segmentation/euclidean_cluster.cpp`](../src/segmentation/euclidean_cluster.cpp)。

### 第 1 段：三个参数校验（第 26–43 行）

```cpp
if (!input || input->empty())
{
    result.summary = "输入点云为空，未执行";
    return result;
}
if (opt.tolerance <= 0.0)
{
    result.summary = "容差必须为正，未执行";
    return result;
}
if (opt.minSize < 1 || opt.minSize > opt.maxSize)
{
    result.summary = "簇大小范围不合法，未执行";
    return result;
}
```

**第三个检查特别重要**：

```cpp
if (opt.minSize < 1 || opt.minSize > opt.maxSize)
```

**为什么 `minSize < 1` 要拦？** 因为 `minSize = 0` 意味着"接受 0 点的簇" ——
虽然没有 0 点的簇，但这个参数没有意义，说明用户填错了。

**为什么 `minSize > maxSize` 要拦？** 因为这样**不可能有簇通过** ——
PCL 不报错，返回空。

**这一类检查的价值**：把"用户填错"和"算法没找到"区分开。
否则你会花半小时怀疑算法，其实只是参数写反了。

### 第 2 段：建 KD-Tree（第 45–49 行）

```cpp
pcl::search::KdTree<PointT>::Ptr tree(new pcl::search::KdTree<PointT>);
tree->setInputCloud(input);
```

**这两行是"把搜索结构准备好，交给聚类去用"。**

**注意这里用的是 `pcl::search::KdTree`**，不是 `pcl::KdTreeFLANN`。

两者有什么区别？

| 类型 | 谁用 | 特点 |
|---|---|---|
| `pcl::KdTreeFLANN` | 你自己调 `nearestKSearch` | FLANN 实现，快，但只能 kNN/半径搜索 |
| `pcl::search::KdTree` | 给 PCL 算法当 `setSearchMethod` | PCL 统一接口，兼容性强 |

**本项目 [10_KDTree](10_KDTree邻域搜索.md) 的演示用的是 `KdTreeFLANN`**（因为要展示具体结果），
**聚类这里用 `search::KdTree`**（因为要给 PCL 内部算法用）。

**这个区别在文档里经常被略过，但它解释了"为什么同一个概念有两个类"。**

### 第 3 段：配置并执行（第 51–60 行）

```cpp
std::vector<pcl::PointIndices> clusterIndices;
pcl::EuclideanClusterExtraction<PointT> ec;
ec.setClusterTolerance(opt.tolerance);
ec.setMinClusterSize(opt.minSize);
ec.setMaxClusterSize(opt.maxSize);
ec.setSearchMethod(tree);
ec.setInputCloud(input);
ec.extract(clusterIndices);
```

**输出类型是 `std::vector<pcl::PointIndices>`** —— 一个"下标的数组的数组"。

```
clusterIndices[0].indices = {3, 7, 11, 15, ...}     ← 第 1 簇的点下标
clusterIndices[1].indices = {0, 1, 2, 5, ...}       ← 第 2 簇的点下标
```

**注意**：PCL 不会给你"新的点云"，只给你**下标**。
要拿到真正的点，得自己按下标去 `input->points[idx]` 取。

**为什么这么设计**：省内存。30251 个点复制一遍要 484 KB，
而只传下标的话，同一份点云可以被多个算法共享。

### 第 4 段：没找到簇（第 62–68 行）

```cpp
if (clusterIndices.empty())
{
    result.summary = "没有找到任何簇";
    printError("没有找到任何簇。常见原因：容差太小（每点都孤立）、minSize 太大");
    printInfo("试试先把容差调到 ~3 倍点间距，minSize 调到 10");
}
```

**这个分支的提示语是"诊断建议"，不只是"出错了"。**

**对比一下**：

- 烂提示：`Error: no clusters found`
- 好提示：`没有找到任何簇。常见原因：容差太小（每点都孤立）、minSize 太大。试试先把容差调到 ~3 倍点间距`

**写代码时多想一步"用户看到这句会怎么想"，比多写 100 行功能更有用。**

### 第 5 段：按点数排序（第 70–75 行）

```cpp
std::sort(clusterIndices.begin(), clusterIndices.end(),
          [](const pcl::PointIndices &lhs, const pcl::PointIndices &rhs)
          { return lhs.indices.size() > rhs.indices.size(); });
```

**PCL 输出的簇顺序是没有意义的**（按"第一个被扫到的点"排）。

**排序之后，"最大的簇"就在第 0 个**，方便：

- 屏幕上先显示最重要的
- 后面直接取 `clusterIndices.front()`

**lambda 里 `>` 是降序。** 如果写成 `<` 就是升序（最小的在前），
那"最大簇"就跑到最后去了。

**这是"排序方向搞反"的经典坑** —— 排序不会报错，结果只是反的。

### 第 6 段：手算重心（第 87–100 行）

```cpp
double sx = 0.0, sy = 0.0, sz = 0.0;
for (const int idx : indices)
{
    const auto &p = input->points[static_cast<size_t>(idx)];
    sx += p.x;
    sy += p.y;
    sz += p.z;
}
const double n = static_cast<double>(indices.size());
const double cx = sx / n, cy = sy / n, cz = sz / n;
```

**重心（centroid）就是"所有点的坐标平均值"：**

$$\bar{x} = \frac{1}{n}\sum_{i=1}^{n} x_i$$

**这里又手写了一遍**（PCL 有 `pcl::compute3DCentroid` 可以直接算）。

**为什么手写**：和 RANSAC 里手写拆点一样 —— **让你看见"重心"到底是什么**。

而且注意：`sx, sy, sz` 用的是 **`double`**，不是 `float`。

**为什么**：累加 25920 个 `float`，误差会累积。用 `double` 累加，
最后再转回 `float` 存进点云，精度高得多。**这是数值计算的基本功。**

`static_cast<size_t>(idx)` 是因为 `idx` 是 `int`，而 `vector` 的下标是 `size_t`。
**不加会有一个"有符号转无符号"的警告**（MSVC 的 C4365）。

### 第 7 段：拼出最大簇和其余点（第 115–143 行）

```cpp
const auto &largest = clusterIndices.front().indices;
```

**`front()` 取第一个** —— 因为上面已按点数降序排序，所以第一个就是最大的。

```cpp
std::vector<bool> inLargest(input->size(), false);
for (const int idx : largest)
{
    inLargest[static_cast<size_t>(idx)] = true;
}
```

**又是"bool 数组打标记"的套路** —— 和 RANSAC 里一模一样。

**这个模式在本项目里出现了三次**（RANSAC 拆分、聚类拆最大簇、聚类拆 rest）。
**值得记住**：PCL 用下标表示"哪些点"，你用 bool 数组把下标翻译成"属不属于"。

### 第 8 段：把重心存成点云（第 145–166 行）

```cpp
CloudPtr centroids(new CloudT);
centroids->reserve(clusterIndices.size());
for (const auto &cluster : clusterIndices)
{
    // ... 手算重心 ...
    centroids->push_back(PointT(static_cast<float>(sx / n), ...));
}
```

**把每簇的重心当成一个"点"，存进一份新的点云。**

结果：2 簇 → 2 个点。

**这个技巧在工业上非常常用**：

- 料框里 50 个零件 → 50 个重心点 → 直接给机器人
- 一帧扫描里有 200 个焊缝段 → 200 个重心点 → 一眼看出分布

**注意 `PointT(...)` 是直接构造**，等价于：

```cpp
PointT p;
p.x = static_cast<float>(sx / n);
p.y = ...;
p.z = ...;
centroids->push_back(p);
```

**这里必须 `static_cast<float>`**，因为 `PointXYZ` 的坐标是 `float`。

### 第 9 段：指标（第 168–176 行）

```cpp
result.metrics["聚类容差(mm)"] = opt.tolerance;
result.metrics["minSize"]      = static_cast<double>(opt.minSize);
result.metrics["簇数"]         = static_cast<double>(clusterIndices.size());
result.metrics["最大簇点数"]   = static_cast<double>(largest.size());
result.metrics["最大簇占比"]   = ... longest.size() / input->size() ...;
```

**`最大簇占比` 是个很有用的指标。**

- 接近 1.0 → 几乎所有点连成一片 → **容差太大，分不开**
- 接近 0 → 最大簇也很小 → **容差太小，全碎成小块**
- 0.5 ~ 0.9 → 合理

**这就是"不看不知道，一看就知道参数对不对"的指标。**

## 九、检查结果是否合理

### 检查 1：簇数和你预期有几个物体一致

本场景：管道 1 个 + 平板 1 个 = **2 个物体 → 2 簇**。

- 得到 2 簇 ✅
- 得到 20 簇 → 容差太小，管道碎了
- 得到 1 簇 → 容差太大，或者两个物体之间有点相连
- 得到 0 簇 → 容差太小 + minSize 太大

### 检查 2：重心位置和你预期的物体位置一致

这是**最快的验证方法**。

本场景的期望：

| 物体 | 理论重心 |
|---|---|
| 管道 | `(0, 0, 0)`（轴沿 X，中心在原点） |
| 平板 | `(0, 200, 0)`（y=200） |

**打印出来一对比就知道对不对。**

**在真实场景里，重心是你唯一能"心算验证"的量** ——
比如"这块钢板应该在工件坐标系 (500, 0, 200) 附近"。

### 检查 3：点数之和 ≈ 输入点数

```
25921 + 4131 = 30052
输入 30251
差 199
```

**差的 199 就是"没能成簇"的飞点 + 被 minSize 过滤掉的碎片。**

**这个账要能算平**：

$$N_{in} = N_{最大簇} + N_{其他簇} + N_{未成簇}$$

如果差得多，说明有大量点没能连上（容差太小）。

### 检查 4：最大簇占比

| 值 | 含义 |
|---|---|
| ≈ 1.0 | 全部连成一片 → 分不开 |
| 0.5 ~ 0.9 | 合理（本场景 0.857） |
| < 0.3 | 碎得厉害 |

### 检查 5：看 `cluster_centroids` 文件

打开它（`output/cluster_centroids_tol3.00_min50.pcd`），**里面只有 2 个点**。

用它检查"物体分布"最直观。

**目标：找到让管道刚好连成一片的最小容差。**

1. 从 2.0 开始，每次加 0.1（2.1、2.2、2.3...），`minSize` 设 50
2. 记录每次的簇数

<summary>预期答案</summary>

## 十一、常见报错与调试

| 现象 | 原因 | 解决 |
|---|---|---|
| 0 簇 | 容差太小 / minSize 太大 | 容差调到 1.5~3 倍点间距 |
| 1 簇（全部连一起） | 容差太大 | 调小 |
| 簇数特别多 | 容差太小，点被切碎 | 同上 |
| 最大簇点数远小于预期 | 同上 | 同上 |
| `minSize > maxSize` 拒绝执行 | 填反了 | 改回来 |
| 程序很慢 | 容差太大导致邻居数爆炸 | 先降采样（体素）再聚类 |
| 内存暴涨 | `maxSize` 设成了天文数字且点很多 | 正常，簇本身就要存下标 |

### 一个隐蔽的现象：簇数对容差极其敏感

看实测表：容差 1.0 → 0 簇，2.0 → 20 簇，3.0 → 2 簇。

**容差只变了 1 mm，结果从"没有"变到"二十块"。**

**这不是 bug，这是聚类算法的本质** —— 它是在找"连通分量的相变点"，
而**相变是突变的**（就像水到 0°C 突然结冰），不是渐变的。

**所以调试聚类的正确姿势**：

1. **先算**理论临界值（斜对角间距）
2. 从"理论值 × 1.5"开始试
3. 不要指望"微调一点点会平滑改善" —— **它是跳变的**

### 另一个坑：`maxSize` 设太小会静默返回空

如果你的 `maxSize = 100`，而所有物体都超过 100 点，
**PCL 返回 0 簇，不报错**。

**本项目的检查已经覆盖了这个**（`minSize < 1 || minSize > maxSize`），
但**"maxSize 太小"这个语义错误拦不住** —— 只能靠你看输出的簇数。

## 十二、与管道焊缝点云处理的联系

### 聚类在焊缝流程里的位置

```
点云 → 预处理 → 分割（工件/背景分离）→ 聚类 → 特征提取
                                    ↑
                                 这一步
```

**具体用法**：

| 用途 | 怎么用 |
|---|---|
| **分离工件与背景** | 台面/夹具是一大簇，工件是另一簇 |
| **多工件识别** | 一框里 20 个管件，聚成 20 簇，输出 20 个重心 |
| **找飞溅/焊渣** | 小尺寸的独立簇 → 按 `minSize`/`maxSize` 筛出来 |
| **区分焊缝段** | 一条焊缝可能被分成几段独立簇（比如中间有缺陷断开） |

### 一个重要限制：焊缝本身往往"连成一片"

**焊缝和母材是连着的** —— 它们之间没有空隙。

所以**欧氏聚类分不开"焊缝"和"母材"**。它只能分开"两个不同的物体"。

**要分焊缝，得用别的方法**：

| 方法 | 依据 |
|---|---|
| 法向突变 | 焊缝两侧法向变化剧烈 |
| 曲率极值 | 焊缝处曲率大 |
| 切片 + 2D 轮廓 | 在截面里找坡口的 V 形 |
| RANSAC 找坡口面 | 找到斜面，斜面之间的就是焊缝 |

**聚类在焊缝流程里真正的角色**：**把工件从背景里分出来**，
而不是"把焊缝从工件里分出来"。

**这一点很容易搞混。** 记住：

> **聚类分的是"物体"，不是"特征"。**

### 工业上"料框抓取"的完整流程

这是聚类最成功的工业应用，和焊缝有一定的相似性：

```
1. 3D 相机拍料框
2. PassThrough 裁掉料框外的部分
3. 体素降采样（提速）
4. 平面分割（去掉台面）
5. 欧氏聚类 → N 个零件
6. 每个簇算重心 + 位姿（PCA）
7. 输出给机器人抓取
```

**注意第 2、3、4 步在前，聚类在中间，位姿在后。**

本项目实现了 2、3、4、5 —— **第 6 步（PCA 算位姿）没做**（见 README 的"未实现"清单）。

## 十三、在真实扫描数据中的局限

### 局限 1：容差必须随距离变化

真实的深度相机 / 线激光，**点间距随距离增长**：

- 距离 500 mm 处，点间距 0.5 mm
- 距离 2000 mm 处，点间距 2.0 mm

**一个固定容差不可能同时合适**：设 0.8 → 远处全断开；设 2.5 → 近处全连成一片。

**工业应对**：

- 把扫描距离控制在一个窄范围内
- 或者先降采样到均匀密度
- 或者用"自适应容差"（很少见，实现复杂）

### 局限 2：薄壁会被"穿孔"

如果物体是薄壁（比如 1 mm 厚的钢板），从一侧扫描时，
**壁的内外表面只隔 1 mm**。

容差设 3 mm → 内外表面**连成一簇**（你本来可能想分开）。
容差设 0.5 mm → 表面上的点自己都连不上。

**薄壁是欧氏聚类最头疼的几何。**

### 局限 3：遮挡导致"断链"

真实扫描有遮挡：物体的一个部分被挡住，扫描不到中间那段。

**结果**：本该是一簇的物体，断成两簇。

**这时候你会看到"簇数比预期多"，但每个簇的几何都对。**
**人眼一看就知道该合并**，但算法不知道。

### 局限 4：对噪声敏感（会粘住飞点）

实测已经验证：容差从 3.0 到 10.0，最大簇点数从 25921 涨到 25925 ——
**多出来的 4 个点全是吸附的飞点**。

**如果飞点成串**（比如扫描反光造成的条纹），甚至可能把两个物体连起来。

**所以：聚类前必须去噪（SOR/ROR），这是硬要求。**

### 局限 5：它不知道"什么是物体"

聚类只按距离分堆，**它不知道一堆点是不是"一个东西"**。

一堆积木散落在地上，每个积木是一簇 —— 好。
一堆积木**挨在一起**，全部连成一簇 —— 你没法拆开。

**这时候需要别的信息**（颜色、形状、法向、甚至模型匹配）。

### 局限 6：`minSize`/`maxSize` 是"硬阈值"

设 `minSize = 50` 意味着"49 点的簇不要"。

但如果真实场景里既有 30 点的**重要缺陷**，又有 45 点的**噪声**，
**同一个阈值不可能区分它们** —— 只能靠别的特征（位置、形状）。
