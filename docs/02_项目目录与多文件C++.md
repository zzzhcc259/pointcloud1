## 一、先看全貌：32 个文件是怎么分的

打开 `src\` 目录，你会看到五个子目录。这不是按"技术难度"分的，是按**职责**分的：

```
src\
├── main.cpp                     ← 入口。58 行，只做三件事
│
├── core\                        ← 【基础设施】和点云算法完全无关的通用件
│   ├── types.h                     一行类型别名
│   ├── algo_result.h               所有算法统一的"返回值长什么样"
│   ├── console.h / console.cpp     中文对齐打印、读用户输入
│   └── cloud_io.h / cloud_io.cpp   PCD 读写、找项目路径、写保护
│
├── data\                        ← 【造数据 + 看数据】
│   ├── scene_presets.h / .cpp      5 套场景参数
│   ├── generate_scene.h / .cpp     按参数生成点云
│   └── inspect_cloud.h / .cpp      点云体检
│
├── preprocessing\               ← 【预处理】删点/改点
│   ├── voxel_filter.h / .cpp
│   ├── statistical_filter.h / .cpp
│   └── radius_filter.h / .cpp
│
├── search\                      ← 【空间搜索】只查邻居，不删点
│   └── kdtree_demo.h / .cpp
│
├── segmentation\                ← 【裁剪与分割】把点分成几组
│   ├── passthrough_demo.h / .cpp
│   ├── ransac_plane.h / .cpp
│   └── euclidean_cluster.h / .cpp
│
└── menu\                        ← 【界面层】菜单
    ├── menu_registry.h / .cpp      菜单框架：编号自动生成、循环、输入校验
    ├── menu_items.cpp              11 个菜单项各自干什么
    └── algo_runner.h / .cpp        "独立跑一个算法"的统一流程
```

### 一条铁律：**依赖只能往下走，不能往上走**

```
                   main.cpp
                      │
        ┌─────────────┴─────────────┐
        ↓                           ↓
   menu\ (界面层)              (将来的 CLI 参数层)
        │
        ↓
  ┌─────┴──────┬──────────┬────────────┐
  ↓            ↓          ↓            ↓
preprocessing search   segmentation  data\      ← 算法层
  └─────┬──────┴──────────┴────────────┘
        ↓
      core\ (基础设施)                            ← 谁都能用，它不用别人
```

**单向依赖的好处**：`core\console.cpp` 永远不会 `#include "segmentation/ransac_plane.h"`。
所以你可以放心把 `ransac_plane.cpp` 整个删掉 —— 除了 `menu_items.cpp` 会编译不过，
其它 31 个文件谁都不受影响。

这个性质叫**低耦合**。它不是什么高级设计模式，就是"别让底层依赖上层"。

### 验证一下这个说法（现在就能做）

```powershell
cd E:\dianyunxulian
Select-String -Path src\core\*.cpp -Pattern "segmentation|preprocessing|search"
```

**预期结果**：一行都搜不到。这就是"`core` 不依赖任何算法层"的证据。

## 二、`.h` 和 `.cpp` 到底各干什么

先看一个真实例子。打开 `src\segmentation\ransac_plane.h`，前面是注释，后面是：

```cpp
#pragma once

#include "core/algo_result.h"

namespace pcp
{

struct RansacPlaneOptions
{
    double distanceThreshold = 1.0;
    int maxIterations = 1000;
    double probability = 0.99;
    bool optimizeCoefficients = true;
};

AlgoResult runRansacPlane(const CloudPtr &cloud, const RansacPlaneOptions &opt);

}  // namespace pcp
```

再打开 `src\segmentation\ransac_plane.cpp`，它的开头是：

```cpp
#include "segmentation/ransac_plane.h"
// ... 一堆 PCL 头文件 ...

namespace pcp
{

AlgoResult runRansacPlane(const CloudPtr &cloud, const RansacPlaneOptions &opt)
{
    // 几百行实现
}

}  // namespace pcp
```

### 分工表

| | `.h`（头文件） | `.cpp`（源文件） |
|---|---|---|
| 里面放什么 | **声明**：告诉别人"有这么个东西，长什么样" | **定义**：它到底怎么干 |
| 典型内容 | `struct` 的**完整定义**、函数**声明**（只有签名带分号）、`constexpr` 常量、`inline` 函数 | 函数体、内部辅助函数、`static` 变量 |
| 会被谁读 | 所有 `#include` 它的 `.cpp` + 编译器 + 你自己 | 只有编译器 |
| 能不能造假 | 不能。写了声明却没有实现，链接时会报错 | 可以有实现但没人调用 |
| 类比 | 菜单（菜名 + 价格 + 用什么料） | 后厨（具体怎么做） |

### 为什么 `struct RansacPlaneOptions` 写在 `.h` 里，而函数体写在 `.cpp` 里？

这和"声明 vs 定义"是两码事，要分开说：

**函数的"声明"和"定义"可以分开**
- `.h` 里：`AlgoResult runRansacPlane(const CloudPtr&, const RansacPlaneOptions&);` ← 声明，只有签名 + 分号
- `.cpp` 里：`AlgoResult runRansacPlane(...) { ... }` ← 定义，有函数体
- **同一个函数可以有多个声明（每次 `#include` 都是一次），但只能有一个定义**

**类型（`struct`、`class`）的"声明"和"定义"却不能随便分开**
- 因为 `menu_items.cpp` 要创建 `RansacPlaneOptions opt;` 这个对象，编译器必须知道它**有多大**（有几个成员、各是什么类型、怎么初始化）
- 如果只在 `.h` 里写 `struct RansacPlaneOptions;`（这叫"前置声明"），编译器只知道"有这么个类型"，不知道它的成员，就没法创建对象、没法访问 `.distanceThreshold`
- 所以 `struct` 的**完整定义**必须放在 `.h` 里，让所有用它的 `.cpp` 都能看到

**一句话记忆**：

> `.h` 里放"别人需要知道的一切"；`.cpp` 里放"只有编译器需要知道的细节"。

### 一个反例：如果把 `struct` 定义在 `.cpp` 里会怎样？

在 `ransac_plane.cpp` 里把 struct 定义删掉、只留 `.h` 里的前置声明，然后编译。你会得到：

```
error C2027: 使用了未定义类型 "pcp::RansacPlaneOptions"
```

因为 `menu_items.cpp` 想 `RansacPlaneOptions opt;` 的时候，编译器不知道这个类型有多大 —— 连栈上分配多少字节都算不出来。

## 三、`#include` 到底是什么

**这是初学 C++ 最容易误解的一条。**

`#include "xxx.h"` **不是**"链接一个模块"，**不是**"导入一个包"。
它就是**把那个文件的内容原封不动地复制粘贴到这一行**。

### 亲眼看看（PowerShell 里就能做）

```powershell
cd E:\dianyunxulian
# 只看 ransac_plane.cpp 展开后有多大
cl /P /nologo /EHsc /std:c++17 /I src /I "E:\PointCloudEnv\PCL\include\pcl-1.15" src\segmentation\ransac_plane.cpp /FoNUL 2>$null
# 生成 ransac_plane.i，看看行数
(Get-Content ransac_plane.i).Count
```

> 如果机器上 `cl` 不在 PATH（没开"开发者命令提示符"），这一步跳过也没关系 ——
> 结论是确定的：`ransac_plane.cpp` 原本 300 多行，预处理后展开成 **几万行**，
> 因为 `#include <pcl/segmentation/sac_segmentation.h>` 又包含了上百个 PCL 头文件。
>
> 想自己确认更简单的版本：数一下 `#include "core/algo_result.h"` 展开后引入了什么 ——
> 打开 `src\core\algo_result.h`，它自己又 `#include <pcl/point_cloud.h>` 等等。

### 两种写法的区别

```cpp
#include <pcl/io/pcd_io.h>      // 尖括号：优先去"系统/第三方头文件目录"找
#include "core/cloud_io.h"      // 双引号：优先去"当前源文件所在目录"找，再找系统目录
```

本项目里：
- 双引号全部用在**自己写的头文件**上，写**相对于 `src\` 的路径**（例如 `#include "core/cloud_io.h"`）
- 尖括号全部用在 **PCL / C++ 标准库**上

**为什么能写 `"core/cloud_io.h"` 而不是 `"../core/cloud_io.h"`？**

因为 `CMakeLists.txt` 里有这一行：

```cmake
target_include_directories(PointCloudPractice PRIVATE src ${PCL_INCLUDE_DIRS})
```

它告诉编译器："找头文件的时候，把 `src\` 也当成一个搜索起点"。
所以 `#include "core/cloud_io.h"` 能被找到 `src\core\cloud_io.h`。

**删掉这一行会怎样？** 所有 `#include "core/..."`、`#include "segmentation/..."` 全部报：

```
fatal error C1083: 无法打开包括文件: "core/algo_result.h": No such file or directory
```

`C1083` = **预处理阶段**找不到文件。这是三阶段（预处理 → 编译 → 链接）里最早的一个阶段，
处理方法和链接错误完全不同，详见 [05_编译链接与调试.md](05_编译链接与调试.md)。

## 四、`#pragma once` 与"重复包含"

### 问题从哪来

假设没有 `#pragma once`，`main.cpp` 这样写：

```cpp
#include "core/algo_result.h"        // 里面又 include 了 types.h
#include "core/cloud_io.h"           // 里面**也** include 了 types.h
#include "menu/menu_registry.h"      // 里面**也** include 了 algo_result.h
```

展开之后，`types.h` 的内容会出现两遍，`algo_result.h` 会出现两遍。
如果这两个文件里定义了 `struct AlgoResult`，编译器第二次见到它就会报：

```
error C2011: "pcp::AlgoResult": "struct" 类型重定义
```

### 解决：每个头文件第一行写 `#pragma once`

本项目**所有 16 个 `.h` 文件的第一行非注释内容都是 `#pragma once`**：

```cpp
// ============ 注释 ============
#pragma once

#include "core/algo_result.h"
```

它的意思是：**这个文件在一次编译单元里只允许被展开一次**，第二次直接跳过。

### 为什么还要了解老写法 `include guard`

`#pragma once` 是编译器扩展（MSVC、GCC、Clang 都支持，但标准没强制）。老代码常用：

```cpp
#ifndef PCP_CORE_ALGO_RESULT_H
#define PCP_CORE_ALGO_RESULT_H
// ... 内容 ...
#endif
```

两者作用相同。**本项目的选择是 `#pragma once`**，因为少三行、不会手抖写错宏名。
你在别的项目里见到 `#ifndef` 不要觉得奇怪，那是同一个东西的旧写法。

### 注意一个陷阱

`#pragma once` 只能防"同一个文件被包含两次"，**防不住"两个不同文件定义了同一个类型"**。

比如你在 `src\core\types.h` 和 `src\data\scene_presets.h` 里各写一遍
`using PointT = pcl::PointXYZ;`，那是 `using` 别名，重复了没关系；
但如果在两个文件里各写一遍 `struct AlgoResult { ... };`，即使都有 `#pragma once`，
`#include` 两者之后照样报 `C2011 类型重定义` —— 因为它们**是两个不同的文件**。

## 五、`main.cpp` 是怎么调用别的文件里的函数的

打开 `src\main.cpp`，全文就这么多（实际 28 行）：

```cpp
#include "core/cloud_io.h"
#include "core/console.h"
#include "menu/menu_registry.h"

#include <iostream>

int main()
{
    pcp::setupConsole();

    std::cout << "项目根目录: " << pcp::projectDir() << "\n";
    std::cout << "原始数据  : " << pcp::toProjectRelative(pcp::originalScenePath()) << "\n";

    const std::vector<pcp::MenuItem> menu = pcp::buildMenu();

    return pcp::runMenuLoop(menu);
}
```

它调用了**三个别的文件里定义的函数**：`setupConsole()`（在 `console.cpp`）、
`projectDir()`（在 `cloud_io.cpp`）、`buildMenu()`/`runMenuLoop()`（在 `menu_registry.cpp`）。

### 为什么这样能行？需要三个条件同时满足

| # | 条件 | 在本项目里是谁保证的 |
|---|---|---|
| 1 | **编译时**：编译器得知道 `pcp::buildMenu` 这个函数存在、参数是什么、返回什么 | 三行 `#include`，把 `.h` 里的函数**声明**展开进 `main.cpp` |
| 2 | **链接时**：`buildMenu` 的实现代码得被编译进最终 exe | `CMakeLists.txt` 的 `target_sources(...)` 里列了 `src/menu/menu_registry.cpp` |
| 3 | **运行前**：`menu_registry.cpp` 用到的 PCL/VTK 的 `.dll` 得能被找到 | `POST_BUILD` 拷 DLL + `env.ps1` 设 PATH |

**这三条**是理解多文件 C++ 的全部精髓。缺任何一条，报错都不一样：

- 只缺条件 1 → `error C3861: "buildMenu": 找不到标识符`
- 只缺条件 2 → `error LNK2019: 无法解析的外部符号 "class std::vector<...> __cdecl pcp::buildMenu(void)"`
- 只缺条件 3 → 编译链接都过，运行时直接退出，退出码 `-1073741515`

### 为什么函数名前都有 `pcp::`

`pcp` 是 `namespace`（命名空间）。`src\core\algo_result.h` 里是这么写的：

```cpp
namespace pcp
{
struct AlgoResult { ... };
}
```

**命名空间的作用**：防止名字撞车。PCL 也有自己的 `PointCloud`，
所以如果本项目不加命名空间，两个 `PointCloud` 一 `#include` 就冲突了。
现在一个是 `pcp::PointT`，一个是 `pcl::PointCloud`，井水不犯河水。

**注意**：命名空间只在 `.h` 和 `.cpp` 里各写一次 `namespace pcp { ... }`，
它不是"另一个文件"，只是名字前缀。函数 `runRansacPlane` 的全名是 `pcp::runRansacPlane`。

## 六、编译 → 目标文件 → 链接 → 可执行文件

这是本项目**最该搞清楚的一张图**。以 `RANSAC` 这个模块为例，它经过四个阶段：

```
① 预处理（Preprocess）
   ransac_plane.cpp  ──展开所有 #include──→  几万行的纯 C++ 代码
   ↓
② 编译（Compile）  ← 每个 .cpp 各自独立编译，互不知情
   ransac_plane.cpp  ──→  build\PointCloudPractice.dir\Release\ransac_plane.obj
   cloud_io.cpp      ──→  build\PointCloudPractice.dir\Release\cloud_io.obj
   main.cpp          ──→  build\PointCloudPractice.dir\Release\main.obj
   ...（20 个 .cpp 就是 20 个 .obj，**每个文件单独编译**）
   ↓
③ 链接（Link）  ← 第一次把所有 .obj 拼起来，检查"每个声明的函数是否都有定义"
   20 个 .obj + pcl_common.lib + pcl_io.lib + ... ──→ PointCloudPractice.exe
   ↓
④ 运行（Run）  ← 加载 .dll，执行
   PointCloudPractice.exe + pcl_common.dll + vtkCommonCore-9.4.dll + ...
```

### 关键结论（每一条都有对应的报错）

| 结论 | 对应的报错 |
|---|---|
| **每个 `.cpp` 单独编译**，不知道别的 `.cpp` 里有什么 | 所以必须 `#include` 别人的 `.h` 才能调用别人的函数（`C3861`） |
| 编译阶段**只检查语法和声明**，不检查实现是否存在 | 所以"声明了没实现"能编译过，链接时才炸（`LNK2019`） |
| 链接阶段**只认"符号名"，不认 .h** | 所以 `.h` 和 `.cpp` 签名写得不一致，会报 `LNK2019`（找不到那个名字） |
| **一个 `.cpp` 改一行，只重编它自己那一个 `.obj`** | 这就是"增量编译"，也是为什么多文件工程改一处不用等全量重编 |
| **一个 `.h` 改一行，所有 `#include` 它的 `.cpp` 全部重编** | 这就是为什么头文件里不要放复杂实现 |
| 生成器换了 / CMakeLists 改了 → 要重新 **configure** | 因为 `.sln`/`.vcxproj` 变了，MSBuild 才知道要编哪些文件 |

### 在磁盘上实际看这些文件


而不是源码目录旁边 —— 这是 CMake 的"源外构建"（out-of-source build）。

## 七、为什么每个算法模块**不能**再定义一个 `main()`

### 一个程序只能有一个 `main`

`main` 是操作系统调用程序的入口。链接器在把所有 `.obj` 拼起来的时候，
**只允许存在一个 `main` 符号**。

如果你在 `ransac_plane.cpp` 里也写一个 `int main() { ... }`，链接时会报：

```
LNK2005: main 已经在 ransac_plane.obj 中定义
LNK1169: 找到一个或多个多重定义的符号
```

（具体是 `LNK2005` 还是 `LNK2019` 取决于顺序，核心都是"两个 main 撞车"。）

### 那如果我就想单独测试 RANSAC 怎么办？

**不要动主程序，用另一个可执行目标。** 本项目已经演示了这种做法：

`practice\CMakeLists.txt` 里有一个**完全独立的可执行目标**：

```cmake
add_executable(exercises exercises.cpp
    ${CMAKE_SOURCE_DIR}/src/core/console.cpp
    ${CMAKE_SOURCE_DIR}/src/core/cloud_io.cpp)
```

`exercises.cpp` 有**自己的 `main()`**，编译出来是另一个 exe（`build\practice\Release\exercises.exe`），
和 `PointCloudPractice.exe` 互不干扰。

**这是多可执行工程的标准做法**：一个 CMake 工程可以有多个 exe，
它们各自有各自的 `main`，但**每个 exe 内部只能有一个 `main`**。

### 反过来说：为什么不建议"每个算法一个 exe"？

本项目选择了"一个菜单 exe + 可选练习 exe"，而不是"7 个算法 7 个 exe"，原因是：

- 7 个 exe 意味着 7 份 `main()`，每加一个算法要改 CMake、改 README、改运行说明
- 七份 `main()` 里"读 PCD → 判空 → 打印点数"的代码会重复七遍
- 用户想对比"同一份数据上不同参数的效果"，得反复切换 exe

但**一个 exe 内部**仍然是"每个算法一个函数、一个文件、互不调用"。
这就是本项目 `src\menu\algo_runner.h` 里那句话的意思：

> ★ 这行代码是"每个算法都独立读原始数据"这条需求的唯一实现位置 ★

打开 `src\menu\algo_runner.cpp`，`runOnOriginalCloud()` 里**每次都重新调用 `loadCloud(originalScenePath(), ...)`**。
菜单里十个算法项，每一个都是走这条路，所以谁也不会读到上一个算法的输出。

## 八、三种典型错误，本项目都能复现

这一节请**真的动手做一遍**。报错看不懂不是因为你笨，是因为没见过。

### 错误 1：`C1083` —— 头文件找不到（预处理阶段）

**制造它**：把 `CMakeLists.txt` 里的

```cmake
target_include_directories(PointCloudPractice PRIVATE src ${PCL_INCLUDE_DIRS})
```

改成

```cmake
target_include_directories(PointCloudPractice PRIVATE ${PCL_INCLUDE_DIRS})
```

（把 `src` 删掉了）

**重新配置 + 构建**：

```powershell
cmake -S . -B build -G "Visual Studio 18 2026" -A x64
cmake --build build --config Release
```

**你会看到**：

```
error C1083: 无法打开包括文件: "core/algo_result.h": No such file or directory
```

**为什么**：`ransac_plane.cpp` 里写的是 `#include "core/algo_result.h"`。
双引号会先找"当前文件所在目录"（`src\segmentation\`），
再找编译器收到的 `-I` 列表（现在只有 PCL 的 include，没有 `src`）。
于是 `src\core\algo_result.h` 找不到了。

**怎么恢复**：把 `src` 加回去，重新配置。

**学到的**：`C1083` 永远在**最早**的阶段报，处理方法只有两种 ——
改 `#include` 的路径，或者加 `-I`（也就是 `target_include_directories`）。

### 错误 2：`LNK2019` —— 未定义引用（链接阶段）

**这是本项目最值得亲手制造一次的错误。**

**制造它**：在 `CMakeLists.txt` 的 `target_sources(...)` 里，把这一行删掉：

```cmake
    src/preprocessing/voxel_filter.cpp
```

**重新配置 + 构建**（注意：改 CMakeLists 必须重新 configure）：

```powershell
cmake -S . -B build -G "Visual Studio 18 2026" -A x64
cmake --build build --config Release
```

**你会看到**（大意）：

```
error LNK2019: 无法解析的外部符号 "struct pcp::AlgoResult __cdecl pcp::runVoxelGrid(
    class std::shared_ptr<class pcl::PointCloud<struct pcp::PointT> const> const &,
    struct pcp::VoxelOptions const &)"
```

**逐字读懂这句话**：

| 部分 | 意思 |
|---|---|
| `LNK2019` | 链接阶段，不是编译阶段 |
| `无法解析的外部符号` | 我在某个 `.obj` 里看到了"要调用 `runVoxelGrid`"，但翻遍所有 `.obj` 和 `.lib` 都找不到它的**实现** |
| `__cdecl` | 调用约定（MSVC 的默认值，了解即可） |
| `pcp::runVoxelGrid` | 找的是这个名字 —— **含命名空间、含参数类型** |
| 最后那串 | 完整的参数类型，用来区分同名重载 |

**为什么编译能过、链接才炸**：`menu_items.cpp` 只 `#include "preprocessing/voxel_filter.h"`，
编译器看到声明就够了 —— "有这么个函数，参数类型对，语法没问题"，编译通过。
到了链接阶段，链接器要把它真正接起来，才发现 `voxel_filter.obj` 压根没参与构建。

**怎么恢复**：把那一行加回去，重新配置 + 构建。

**学到的**：`LNK2019` 只有一个含义 —— **"有人要用，但没人实现"**。
排查顺序：

1. 那个函数的实现文件，加进 `target_sources` 了吗？（最常见）
2. `.h` 里的声明和 `.cpp` 里的定义，**参数类型和 const 完全一致**吗？
3. 实现文件在 `namespace pcp` 里面吗？（忘了写 `namespace` 会导致符号名变成 `::runVoxelGrid`，链接器按 `pcp::runVoxelGrid` 找就找不到）

> 第 3 条特别容易踩。`LNK2019` 里显示的符号名，就是**链接器真正在找的名字**。
> 如果它显示的是 `runVoxelGrid` 而不是 `pcp::runVoxelGrid`，说明声明那边没在 namespace 里。

### 错误 3：`LNK2005` —— 重复定义

**制造它**：在 `src\core\console.cpp` 里把 `printRule()` 的实现复制一份，
粘贴到 `src\core\cloud_io.cpp` 末尾，函数体一个字不改。

**构建**（这次不用重新 configure，只改了 `.cpp`）：

```powershell
cmake --build build --config Release
```

**你会看到**：

```
error LNK2005: "void __cdecl pcp::printRule(void)" (?printRule@pcp@@YAXXZ) 已经在 console.obj 中定义
```

**为什么**：两个 `.obj` 里各有一份 `pcp::printRule` 的实现，链接器不知道该用哪个。
注意它和 `LNK2019` 是**相反**的问题 —— 一个是"没有实现"，一个是"实现太多了"。

**怎么恢复**：把复制的那份删掉。

**学到的**：**非 `inline` 函数的定义只能出现在一个 `.cpp` 里**。
如果你需要在头文件里写函数体（比如一行的小工具函数），必须加 `inline`：

```cpp
// 在 .h 里可以这样写
inline int square(int x) { return x * x; }
```

## 九、五个"最小改动"验证练习

每个都只改 1~5 行，改完就知道自己懂没懂。

### 练习 1：验证"声明与定义分离"（5 分钟）

打开 `src\core\console.h`，找到 `void printRule();` 这一行删除（只删 `.h` 里的声明）。

**预期**：`main.cpp` 或别的调用 `printRule()` 的地方报 `error C3861: "printRule": 找不到标识符`。

**恢复**：加回去。

**这说明**：编译器**只认 `.h` 里的声明**。`.cpp` 里那个实现写得再完美，没有声明也调不到。

### 练习 2：验证"命名空间必须一致"（5 分钟）

打开 `src\preprocessing\voxel_filter.cpp`，删掉文件末尾的 `}  // namespace pcp`（让 `runVoxelGrid` 暴露在全局）。

**预期**：`error LNK2019: 无法解析的外部符号 "struct pcp::AlgoResult __cdecl pcp::runVoxelGrid(...)"`

**关键观察**：仔细看报错里找的名字是 `pcp::runVoxelGrid`（带命名空间），
而你现在的定义变成了 `runVoxelGrid`（不带）。**名字对不上 = 链接器找不到**。

**恢复**：加回 `}`。

### 练习 3：验证"头文件的改动会引发大范围重编"（10 分钟）

```powershell
# 全量重编一次，记下耗时
Measure-Command { cmake --build build --config Release } | Select-Object TotalSeconds

# 只在 algo_result.h 里加一行注释
Add-Content E:\dianyunxulian\src\core\algo_result.h "// test"

# 再编一次
Measure-Command { cmake --build build --config Release } | Select-Object TotalSeconds
```

**预期**：第二次比第一次慢很多（接近全量），因为 `algo_result.h` 被 8 个 `.cpp` 包含。

**这说明**：头文件改动的代价是"包含它的所有文件都要重编"。
这是为什么 PCL 的头文件那么大、编译那么慢。

### 练习 4：验证"每个 .cpp 独立编译"（10 分钟）

打开 `src\preprocessing\voxel_filter.cpp`，在文件顶部加：

```cpp
#include "segmentation/ransac_plane.h"
```
然后试着调用 `runRansacPlane(...)`。

**你会发现**：编译通过、链接通过 —— 只要 `ransac_plane.cpp` 在 `target_sources` 里。
也就是说 **`preprocessing` 层可以直接调 `segmentation` 层**。

**这是不是说明"依赖只能往下走"是假的？**

不是。**编译器不管你，是规矩管你。** 单向依赖是人定的约定，不是语言强制的。
一旦你开了这个头，`preprocessing` 就依赖了 `segmentation`，
将来想单独复用 `preprocessing` 就带不走 —— 这才是"低耦合"的真实意义。

**请把这个改动撤销。**

### 练习 5：把 `main.cpp` 的作用替换掉（5 分钟）

在 `src\main.cpp` 的 `buildMenu()` 之后、`runMenuLoop()` 之前加一行：

```cpp
    pcp::printInfo("我改了 main.cpp");
```

重新构建、运行。

**预期**：每次启动，在最上面多打印一行「我改了 main.cpp」，菜单照常工作。

**这说明**：`main.cpp` 就是普通的一个 `.cpp`，它没有什么魔法。
它唯一特殊的身份是"提供 `main()` 这个函数给操作系统当入口"。

**请把这行删掉。**

### 为什么要用 Debug 而不是 Release

| | Debug | Release |
|---|---|---|
| 优化 | 关闭（`/Od`） | 全开（`/O2`） |
| 断点 | 想下就下，变量都能看 | 变量常常显示"已优化掉"，断点可能乱跳 |
| 体积 | 大（带完整调试信息 `.pdb`） | 小 |
| 速度 | 慢 5~20 倍 | 快 |
| PCL 库 | 用 `pcl_common-gd.lib` / `pcl_common-gd.dll` | 用 `pcl_common.lib` / `pcl_common.dll` |

**关键点**：Debug 和 Release 用的是**两套不同的 PCL 库文件**。
本项目的 PCL 1.15.1 恰好两套都有，所以两种配置都能编。
如果你的库只有 Release 一套，Debug 配置会在链接时找不到 `-gd` 后缀的 `.lib`。

## 十一、怎么加一个新算法模块而不破坏现有工程

假设你想加 **`StatisticalOutlierRemoval` 的一个变体**，叫"中值滤波"，
放在新文件 `src\preprocessing\median_filter.h/.cpp`。

### 七步清单（照做就行，20~30 分钟）

#### 第 1 步：建 `.h`

内容照抄 `src\preprocessing\voxel_filter.h` 的结构：

```cpp
#pragma once

#include "core/algo_result.h"

namespace pcp
{

struct MedianOptions
{
    int k = 10;              // 邻域大小
};

AlgoResult runMedianFilter(const CloudPtr &cloud, const MedianOptions &opt);

}  // namespace pcp
```

**注意**：`#pragma once` 别忘了，`namespace pcp` 别忘写。
结构体的成员要有**默认值**，这样调用方可以只改想改的那个。

#### 第 2 步：建 `.cpp`

```cpp
#include "preprocessing/median_filter.h"
// 需要什么 PCL 头文件就 include 什么

namespace pcp
{

AlgoResult runMedianFilter(const CloudPtr &cloud, const MedianOptions &opt)
{
    AlgoResult result;
    // ... 实现 ...
    return result;
}

}  // namespace pcp
```

**关键**：函数签名必须和 `.h` 里**一个字都不差**（包括 `const`、`&`、参数名可以不同但类型必须一致）。

#### 第 3 步：加进 CMake 的 `target_sources`

打开根目录 `CMakeLists.txt`，找到 `target_sources(PointCloudPractice PRIVATE` 那段，
在 `src/preprocessing/` 那几行后面加一行：

```cmake
    src/preprocessing/median_filter.cpp
```

**不加会怎样**：`LNK2019`（见第八节错误 2）。这是最容易漏的一步。

#### 第 4 步：在菜单里加一项

打开 `src\menu\menu_items.cpp`，参照 `actionVoxelGrid()` 写：

```cpp
void actionMedianFilter()
{
    MedianOptions opt;
    opt.k = readInt("邻域大小 k", opt.k);
    runOnOriginalCloud("中值滤波", [&opt](const CloudPtr &cloud) {
        return runMedianFilter(cloud, opt);
    });
}
```

**注意 lambda 捕获 `[&opt]`**：`runOnOriginalCloud` 内部会调用这个 lambda，
`opt` 是局部变量，用引用捕获即可（调用是同步的，不会悬垂）。

#### 第 5 步：在 `buildMenu()` 里注册

在 `src\menu\menu_items.cpp` 的 `buildMenu()` 里加一行：

```cpp
    items.push_back({"滤波", "6  中值滤波（实验性）", actionMedianFilter});
```

（具体分类名和编号你自己定，编号是自动生成的，不用手写数字。）

#### 第 6 步：重新配置 + 构建

```powershell
cmake -S . -B build -G "Visual Studio 18 2026" -A x64
cmake --build build --config Release
```

**为什么第 6 步要重新 configure**：因为改了 `CMakeLists.txt`。
如果只是改 `.cpp` 里的一行，直接 `cmake --build` 就够了。

#### 第 7 步：跑一遍，确认

```powershell
.\build\Release\PointCloudPractice.exe
```

**必须确认三件事**：

1. 菜单上出现你新加的那一项，编号没和别的冲突
2. 选它，能跑完、能打印点数、`output\` 里多了一个文件
3. **`data\scene_original.pcd` 的修改时间没变**（说明没被覆盖）

### 常见卡点

| 症状 | 原因 |
|---|---|
| `C3861: "runMedianFilter": 找不到标识符` | `menu_items.cpp` 里忘了 `#include "preprocessing/median_filter.h"` |
| `LNK2019` | `target_sources` 漏了 `.cpp`，或签名不完全一致 |
| 菜单没变化 | 没重新 compile，或 `buildMenu()` 里那行写在了 `return items;` 之后 |
| 编译过了但运行崩溃 | 空指针没判（`cloud->empty()` 要先查） |

## 十二、小结：三句话

1. **`.h` 放"别人需要知道的"，`.cpp` 放"具体怎么做"** —— 声明可以有多个，定义只能一个。
2. **`#include` 就是复制粘贴** —— 所以需要 `#pragma once`，也需要 `target_include_directories` 告诉编译器去哪找。
3. **编译按文件、链接按符号** —— 每个 `.cpp` 各自变成 `.obj`；
   链接器只认名字（含命名空间），谁给不出名字就报 `LNK2019`。
