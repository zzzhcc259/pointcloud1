## ⚠️ 先纠正一个最常见的误解

**KD-Tree 不是滤波算法。**

| | 滤波（VoxelGrid / SOR / ROR） | KD-Tree |
|---|---|---|
| 会删掉点吗 | **会** | **不会，一个都不删** |
| 会改坐标吗 | VoxelGrid 会 | **不会** |
| 输出是什么 | 一份新的点云 | **下标列表 + 距离** |
| 干什么用 | 清理数据 | **回答"谁挨着谁"** |

**本项目菜单把它放在"空间搜索（不删点）"分组下，就是为了强调这一点。**

那为什么它总和滤波混在一起讲？因为**所有滤波内部都要找邻居**：

```
SOR（统计滤波）
  └── 对每个点：找 20 个最近邻 → 算平均距离     ← 用的就是 KD-Tree
ROR（半径滤波）
  └── 对每个点：找 3mm 内所有点 → 数个数        ← 用的也是 KD-Tree
欧氏聚类
  └── 从种子点扩散：找容差内所有点              ← 还是 KD-Tree
法向估计 / 曲率
  └── 找局部邻域 → 拟合平面                    ← 还是 KD-Tree
```

**KD-Tree 是"地基"，不是"工序"。**

## 1. 它解决什么问题

**问题**：在一堆点里找"离某个位置最近的那些点"。

**朴素做法（暴力搜索）**：和每一个点算距离，排序，取前 k 个。

```cpp
// 暴力 KNN 的伪代码
for (每个点 p in 点云)              // n 次循环
{
    d = 距离(p, 查询点);
    if (d < 第 k 小的距离) 插入候选;
}
```

**复杂度 O(n)**。n = 30251 时，查一次要 30251 次距离计算。

**这看起来不慢**（3 万次浮点运算，微秒级）。但问题是：

- SOR 要对**每一个点**都查一次 → n × n = **9 亿次距离计算**
- 欧氏聚类要从每个种子点扩散 → 也是几亿次

**所以我需要一种"不用看所有点"的搜索方法。**

**KD-Tree 的作用：把 O(n) 降到 O(log n)。**

查一次从 30251 次比较变成约 15 次比较。

## 2. 直观几何解释

### 核心思想：切豆腐，然后只找"可能装得下目标"的那几块

假设二维平面上一堆点，你要找离红点最近的 3 个：

```
    •   •        •   •
       •    •          ← 一堆点
  •       •     •   •
      •              •
   •      ★            ← 查询点
      •    •      •
```

**暴力法**：全部量一遍距离。

**KD-Tree 的做法**：

**第 1 步：建树（用一条条竖线/横线把空间切开）**

```
        │                    ← 用 x = 中位数 竖切一刀
   •    │ •        •   •
        │   •          
  •     │   •     •   •
        │              
   •    │   ★          
        │ •    •      •
```

左边一半、右边一半。**递归地继续切**：

```
        │         │
   •    │ •   │   •   •
        │     │       
  •     │ •   │ •   •
        │     │       
        │     │       
   •    │ •   │ ★     
        │     │ •   •  
```

最后每个小格子里只剩一两个点。**这就是树的最底层（叶子）。**

**第 2 步：查询（只走"可能更近"的那几支）**

从根开始：

```
查询点 ★ 在根切线的右边 → 先搜右边
在右边子树的切线下面 → 先搜下面
...
走到叶子，找到最近的候选（比如距离 3.2）
```

**关键的一步（这是 KD-Tree 的全部精髓）**：

> 搜完一支后，**回头检查另一支** —— 但只检查"到分界线的距离 < 当前最优距离"的那一支。

```
        │
        │   ★ 当前最优 = 3.2
    •   │  ┌─┐
        │  └─┘   ← 分界线距离 = 1.5 < 3.2，所以左边也可能有更好的，要搜
    •   │
```

**如果分界线距离 > 当前最优，就可以整支剪掉（pruning）。**

**这就是为什么 KD-Tree 快**：**大量的点在"完全不用看"的状态下被跳过了。**

### 三维里就是"切七刀"的推广

一维：一个点（切一刀分两段）
二维：一条线（切一刀分两块）
三维：一个平面（切一刀分两块）

**三维 KD-Tree 还是每层切一刀，只是这一刀是一个平面。**

## 3. 必要数学

### 3.1 点与点的距离

三维欧氏距离：

$$
d(p, q) = \sqrt{(p_x - q_x)^2 + (p_y - q_y)^2 + (p_z - q_z)^2}
$$

**但代码里比的是"距离的平方"**（省掉开根号）：

$$
d^2(p,q) = (p_x-q_x)^2 + (p_y-q_y)^2 + (p_z-q_z)^2
$$

**为什么可以只比平方？** 因为 $\sqrt{\cdot}$ 是单调递增函数：
$a < b \iff a^2 < b^2$（当 $a,b \ge 0$）。

**所以"第 3 近的点"和"平方距离第 3 小的点"是同一个点。** 排序结果完全一致。

**这个优化不是多余的**：SOR 要算 30251 × 20 = 60 万次距离，
开根号一次约 10~20 个时钟周期，省下来就是几毫秒。

**但代价是：你拿到的数字不是距离，是距离平方。**

**这是 PCL 里最容易出错的坑之一** —— 见第 7 节。

### 3.2 复杂度

| | 暴力（线性扫描） | KD-Tree |
|---|---|---|
| 建树 | 0（不建） | **O(n log n)** |
| 单次查询 | O(n) | O(log n)（近似，最坏 O(n)） |
| 查 m 次 | O(mn) | O(n log n + m log n) |

**本项目的实际数字**：

- n = 30251
- 暴力：查 1 次 ≈ 30251 次距离计算
- KD-Tree：查 1 次 ≈ **log₂(30251) ≈ 15 次**

**差 2000 倍。**

**但注意"建树"这个成本**：

| 场景 | 该用什么 |
|---|---|
| 只查 1 次 | **暴力可能更快**（建树 30251×15 次操作 > 30251 次比较） |
| 查 1000 次以上 | **KD-Tree 完胜** |

**这就是为什么 KD-Tree 一定要"建一次，查很多次"。** 代码里也这么注释了
（`src/search/kdtree_demo.cpp:44-46`）。

### 3.3 在本项目里的实际查询

**查询点**：`(0, 50, 0)`

**为什么选这个点？** 因为管道轴是 X 轴、θ=0 指向 +Y，半径 50。
所以 `(0, 50, 0)` **恰好在外管壁上**（x=0 是管道中截面附近）。

**最近的 8 个邻居，实测**：

| 序号 | 点坐标 (x, y, z) | 距离 (mm) |
|---|---|---|
| 1 | `(1.45, 50.01, 0.12)` | **1.4600** |
| 2 | `(-1.62, 50.00, -0.05)` | 1.6188 |
| 3 | `(1.43, 49.88, -1.37)` | 1.9814 |
| 4 | `(-1.47, 49.98, 1.35)` | 1.9962 |
| 5 | `(-1.51, 49.93, -1.34)` | 2.0137 |
| 6 | `(1.59, 49.83, 1.31)` | 2.0697 |
| 7 | `(-1.45, 49.90, -2.46)` | 2.8585 |
| 8 | `(-1.42, 49.88, 2.63)` | 2.9869 |

**这 8 个点全是原始点云里的真实点**（坐标都没变），
而且**全都贴在管壁上**（$y^2+z^2 \approx 50^2$）：

- 点 1：$50.01^2 + 0.12^2 = 2501.01$，$\sqrt{} = 50.010$
- 点 3：$49.88^2 + 1.37^2 = 2489.89$，$\sqrt{} = 49.899$
- 点 8：$49.88^2 + 2.63^2 = 2494.93$，$\sqrt{} = 49.949$

**都在 50 ± 0.1 内 —— 这就是"噪声 σ=0.05 加一点圆离散化误差"的结果。**

### 3.4 为什么最近距离是 1.46 而不是 1.309？

**采样网格的间距**是：

- **环向**：240 个点布满 $2\pi$ → 角度步长 $360/240 = 1.5°$
  → 弧长 $= 2R\sin(\Delta\theta/2) = 2\times50\times\sin(0.75°) = 1.309$ mm
- **轴向**：`axialStep = 1.5` mm

**所以理论最近邻距离是 min(1.309, 1.5) = 1.309 mm。**

**实测 1.4600 mm，比 1.309 大了 11.5%。**

**为什么？** 因为：

1. **噪声**（σ = 0.05，三轴独立）会让两点距离抖动，但抖动幅度只有 ±0.07 左右，
   不足以解释 0.15 的差
2. **环向是"弦"不是"弧"**：我上面算的 1.309 已经是弦长了
3. **真正的解释**：管道是**两层**（外表面 r=50，内表面 r=38），
   但内表面点在 r=38 处，与查询点距离 12mm，不会进前 8 名
4. **最可能的原因**：θ 的采样点位置和查询点 (0, 50, 0) 不完全对齐 ——
   查询点在 θ=90° 处（y=50, z=0 就是 θ=90°），而管壁采样点的 θ 值是离散的，
   最近的几个 θ 采样值平均偏 0.1°~0.2°，导致距离偏大

**实测值 1.4600 落在 1.309（环向）和 1.5（轴向）之间 —— 说明最近邻有时来自环向、
有时来自轴向，取决于局部噪声把哪个拉近了。**

**这个 11% 的差不是 bug，是"理想网格 + 随机噪声"的正常表现。**

### 3.5 半径搜索的容量估算

**实测**：半径 5mm 内共 **34** 个点。

**理论估算**：球与管壁曲面相交，近似是一个半径 $\sqrt{r^2 - (\text{弯曲引起的偏差})^2}$ 的圆盘。

球半径 5mm 远小于管道半径 50mm → **曲面在 5mm 尺度上几乎是平的** → 近似圆盘面积：

$$
A \approx \pi r^2 = \pi \times 25 = 78.5 \text{ mm}^2
$$

每个点占的面积 ≈ 环向间距 × 轴向间距 = $1.309 \times 1.5 = 1.96$ mm²

$$
\text{点数} \approx \frac{78.5}{1.96} \approx 40
$$

**实测 34，比估算少 15%。**

**为什么少？**

1. 球心在管壁上，球的一半跑到管道**内部**去了（那里没有点）
   所以真正有效的不是整个圆盘，而是**球被曲面切出来的一侧**
2. 边界的点被"切掉"（圆盘边缘外的邻居不完整）

**"34 vs 40" 这种 15% 的差，是估算模型（把球当圆盘）的固有误差，完全正常。**

## 5. 关键参数

### KNN：`src/search/kdtree_demo.h`

```cpp
struct KdtreeOptions
{
    float qx = 0.0f;   // 查询点 X
    float qy = 50.0f;  // 查询点 Y
    float qz = 0.0f;   // 查询点 Z
    int   k  = 8;      // 要几个最近邻
};
```

| 参数 | 含义 | 默认值 | 说明 |
|---|---|---|---|
| `qx, qy, qz` | 查询点坐标（mm） | `(0, 50, 0)` | **本场景恰好落在管壁上** |
| `k` | 要几个邻居 | 8 | 1 ~ 总点数 |

**为什么默认查询点在管壁上？** 因为如果在空中（比如 `(0, 200, 0)`），
最近的 8 个点距离会是几十 mm，**看不出"局部密度"**。
在管壁上查询，最近的邻居距离 ≈ 点间距 —— 这才是真实的场景。

**代码里的检查**（`kdtree_demo.cpp:30-39`）：

```cpp
if (opt.k < 1) → 报错
if (opt.k > 输入点数) → 警告，自动缩小到总点数
```

**为什么 k 太大只警告不报错？** 因为"要 10 万个最近邻但只有 3 万个点"时，
**返回全部 3 万个点是个合理的降级** —— 用户可能只是想"看看全部"。

### 半径搜索：`KdtreeRadiusOptions`

```cpp
struct KdtreeRadiusOptions
{
    float  qx = 0.0f;
    float  qy = 50.0f;
    float  qz = 0.0f;
    double radius     = 5.0;   // 搜索半径（mm）
    int    maxResults = 50;    // 控制台最多显示多少行
};
```

| 参数 | 含义 | 默认值 | 调大 | 调小 |
|---|---|---|---|---|
| `radius` | 搜索半径 | 5.0 mm | 命中更多点 | 命中更少 |
| `maxResults` | 控制台最多打印几行 | 50 | 打印更多 | 打印更少 |

**`maxResults` 只影响"打印多少行"，不影响"实际找到多少点"。**

**为什么要有它？** 因为半径设成 100mm 时会命中 3 万个点，
全部打印会把控制台刷爆。代码里会提示：

```
半径 5mm 内共 34 个点：

半径 100mm 内共 30000 个点（只显示前 50 个）：
```

**注意输出的 PCD 文件仍然只存了 `maxResults` 个点**（`kdtree_demo.cpp:154-155`），
不是全部命中点。**这是一个设计取舍** —— 想看全部命中的话，把 `maxResults` 设大。

## 6. 参数变大或变小会怎样

### k 变大

| k | 预期 |
|---|---|
| 1 | 只有最近的一个点（距离 1.46） |
| 8（默认） | 距离 1.46 ~ 2.99，**覆盖了最近 2 个网格单元** |
| 20 | 距离到 ~4mm，**覆盖椭圆形的邻域** |
| 30（SOR 的默认值的一半） | 距离到 ~5mm |
| 30000 | 全部点，最远 500+ mm（包括管道另一侧） |

**观察**：k 从 8 增到 20，最远距离从 2.99 到约 4（**不线性**）。

**为什么？** 因为邻居的分布是**面状的**（管壁是个曲面），
k 个邻居围成的区域面积 ∝ k，所以半径 ∝ √k：

$$
\frac{2.99}{\sqrt{8}} \approx 1.06,
\qquad k=20 \Rightarrow 1.06\sqrt{20} \approx 4.7
$$

**实测 k=20 时的最远距离应该在 4.5 左右**（这个数你可以自己跑一遍验证）。

### 半径变大

| radius | 命中点数（实测/估算） |
|---|---|
| 1.0 | 1~2（只有最近的一个点勉强） |
| 2.0 | 约 5 |
| 3.0 | 约 13 |
| 5.0 | **34（实测）** |
| 10.0 | 约 137 |
| 20.0 | 约 550 |
| 50.0 | 约 3400（半个管道） |

**点数 ∝ r²（面积）**，所以半径翻倍 → 点数约 4 倍。

**这个"平方关系"是要记住的**：调半径时很容易不小心从 34 个点变成 3400 个点。

### 查询点位置的影响

| 查询点 | 最近距离 |
|---|---|
| `(0, 50, 0)` 管壁上 | 1.46 mm |
| `(0, 0, 0)` 管道轴线上 | **12 mm**（到内壁距离，因为内半径是 38） |
| `(0, 200, 0)` 平板上 | 约 2.0 mm（平板步长 2.0） |
| `(0, 0, 200)` 空中（附近只有飞点） | **几十 mm**（最近的是飞点） |

**这个练习很有价值**：它让你看到"最近邻距离"直接反映**局部密度**。
在空气里查，最近邻距离会突然变成几十毫米。

## 7. 本项目的代码逐段解释

打开 `src/search/kdtree_demo.cpp`（197 行，两个函数）。

### 第 1 段：KNN 的参数检查（24-39 行）

```cpp
if (!input || input->empty())
{
    result.summary = "输入点云为空，未执行";
    printError("输入点云为空");
    return result;
}
if (opt.k < 1)
{
    result.summary = "k 太小，未执行";
    printError("k 至少为 1");
    return result;
}
if (opt.k > static_cast<int>(input->size()))
{
    printWarn("k 比总点数还大，会自动缩小到总点数");
}
```

**`static_cast<int>(input->size())` 为什么需要？**

`input->size()` 返回 `size_t`（无符号），`opt.k` 是 `int`（有符号）。
**有符号和无符号比较时，C++ 会把有符号的转成无符号** —— 如果 `k` 是负数，
转成无符号后会变成一个巨大的正数，比较结果就反了。

**所以显式转成 int 再比，避免这个坑。**

### 第 2 段：构造查询点（41 行）

```cpp
const PointT query(opt.qx, opt.qy, opt.qz);
```

**`PointT` 是 `pcl::PointXYZ`**，它有个构造函数接受 `(x, y, z)`。

**这一行有个坑**：`PointXYZ` 的构造函数不初始化 `data[3]`（对齐用的填充位），
所以 `query.data[3]` 是未定义的值。**但 KD-Tree 只用 x/y/z，不受影响。**

### 第 3 段：建树（47-48 行）

```cpp
pcl::KdTreeFLANN<PointT> kdtree;
kdtree.setInputCloud(input);
```

**`pcl::KdTreeFLANN`** 是 PCL 里最常用的 KD-Tree 实现（底层是 FLANN 库）。

**`setInputCloud` 是"建树"** —— 这行会遍历所有点，按各维度的中位数递归划分。
**30251 个点的建树大约 10~30 毫秒。**

**建完树之后，`input` 不能再变** —— 如果点云内容改了，树就失效了。
**本项目的流程符合这个约束**（读一次、建一次、查一次）。

**`KdTreeFLANN` vs `pcl::search::KdTree`**：

| | `pcl::KdTreeFLANN<PointT>` | `pcl::search::KdTree<PointT>` |
|---|---|---|
| 层 | `pcl/kdtree/` | `pcl/search/` |
| 用于 | 手工调用搜索 | **作为参数传给其他算法**（如 `EuclideanClusterExtraction`） |
| 本项目 | KNN、半径搜索 | 欧氏聚类内部用 |

**本项目的两个都用了**（`kdtree_demo.cpp` 用前者，`euclidean_cluster.cpp` 用后者）。
**看到这两行 include 不要困惑，它们干的是同一件事。**

### 第 4 段：查询（51-59 行）

```cpp
std::vector<int>   indices;
std::vector<float> sq_distances;

const int k = std::min<int>(opt.k, static_cast<int>(input->size()));
const int found = kdtree.nearestKSearch(query, k, indices, sq_distances);
```

**这是整个算法最关键的四行。**

**`nearestKSearch(query, k, indices, sq_distances)`**：

- 输入：查询点、k
- 输出：`indices`（邻居在**输入点云里的下标**）、`sq_distances`（**平方**距离）
- 返回：**实际找到的个数**（通常等于 k，除非点云里有 NaN）

**为什么输出是"下标"而不是"点坐标"？**

因为**下标更有用**：

- 你可以用 `input->points[idx]` 取回完整的点（包括可能在 `PointXYZI` 里的强度）
- 你可以知道"这个邻居在原数组的第几个"
- **不用拷贝点数据**（省内存）

**`std::min<int>(...)` 为什么需要？** 前面已经检查过 `k > size`，但那次只警告，
没改 `k`。这里再夹一次，保证 `k` 不超过总点数（否则 PCL 会返回 0 或崩溃）。
**这是"警告了但还是要防着"的防御性写法。**

**`sq_distances` 的类型是 `std::vector<float>`，不是 double。**
PCL 内部用 float 算距离（点坐标就是 float），精度约 7 位有效数字。
**对本项目（mm 级，3 万点）完全够用。**

### 第 5 段：处理"没找到"（61-66 行）

```cpp
if (found <= 0)
{
    result.summary = "没有找到任何邻居";
    printWarn("没有找到邻居，可能是点云里全是 NaN");
    return result;
}
```

**什么时候会 `found == 0`？**

- 点云全是 NaN/Inf
- 点云是空的（前面已挡）
- 查询点是 NaN（比如用户输入了 `nan`）

**`nearestKSearch` 返回 0 而不是报错** —— PCL 的风格是"返回码"，不是异常。
**所以每次调用后都要检查返回值。**

### 第 6 段：收集邻居（69-70 行）

```cpp
CloudPtr neighbors(new CloudT);
neighbors->reserve(static_cast<size_t>(found));
```

**`reserve(n)` 预分配 n 个点的内存**（但不改变 size）。

**为什么需要？** 如果不 reserve，`push_back` 会反复扩容（每次扩到 2 倍，
重新分配 + 拷贝）。8 个点无所谓，但如果 k = 30000，就会拷贝很多次。

**这是个好习惯，但不是必须。** 3 万点的 `push_back` 不 reserve 也就慢几毫秒。

### 第 7 段：打印表格（72-100 行）

```cpp
std::cout << "    " << padRight("序号", 8)
          << padRight("点坐标 (x, y, z)", 30)
          << padRight("平方距离", 14)
          << "真实距离\n";
```

**`padRight(s, n)`** 是 `src/core/console.cpp` 里的辅助函数 ——
按**显示宽度**把字符串补到 n 列（中文算 2 列）。

**为什么不用 `std::setw`？** 因为 `std::setw` 数的是**字节数**。
"序号" 在 UTF-8 里是 6 个字节，但显示宽度是 4 列。**用 setw 会错位。**

**（这个坑是开发过程中实际踩到的，才写了 `padRight`。）**

```cpp
for (int i = 0; i < found; ++i)
{
    const PointT &p = input->points[static_cast<size_t>(indices[static_cast<size_t>(i)])];
```

**这一行长，但结构简单**：

1. `indices[i]` 是 `int`（邻居下标）
2. `static_cast<size_t>(...)` 转成无符号（因为 `points[]` 的下标是 `size_t`）
3. `input->points[下标]` 取到点
4. `const PointT &p` **引用**绑定它（不拷贝）

**为什么要 `static_cast<size_t>`？** 直接用 `int` 下标会触发
警告 `C4365: 从 "int" 到 "size_t" 的有符号/无符号不匹配`。
**本项目编译选项没关这个警告，所以必须转。**

```cpp
    // 注意 sqrt：PCL 给的是平方距离
    const double sq = static_cast<double>(sq_distances[static_cast<size_t>(i)]);
    const double dist = std::sqrt(sq);
```

**这就是第 3 节强调的"平方距离坑"在代码里的处理。**

**如果不 sqrt 会怎样？** 打印的"距离"会是 2.13 而不是 1.46 ——
**你不会立刻发现错，因为 2.13 看起来也像个正常的距离。**

**这是最危险的一类 bug：不崩溃、不报错、结果看起来合理。**

**防御方法**：变量名里带 `sq`（squared 的缩写），一眼能看出"这是平方"。

### 第 8 段：设置 width/height（102-104 行）

```cpp
neighbors->width  = static_cast<uint32_t>(neighbors->size());
neighbors->height = 1;
neighbors->is_dense = true;
```

**`pcl::PointCloud` 有 `width` / `height` / `points` 三个"互相独立"的字段。**

**`push_back` 只改 `points`，不改 `width`！**

**如果不设 `width`，会发生什么？**

`width` 还是 0（默认值）→ `savePCDFileBinary` 会写出 `WIDTH 0` →
读回来时 `points` 数组是空的（PCL 按 width 分配）。

**这是 PCL 里最隐蔽的坑之一。** 表现是"存了 8 个点，读回来 0 个"。

**本节的三行是必须的。**

### 第 9 段：指标（107-114 行）

```cpp
result.metrics["最近点距离(mm)"] = std::sqrt(static_cast<double>(sq_distances[0]));
result.metrics["最远邻居距离(mm)"] =
    std::sqrt(static_cast<double>(sq_distances[static_cast<size_t>(found - 1)]));
```

**`sq_distances[0]` 是最近的**（PCL **保证返回结果按距离升序**）。

**`sq_distances[found - 1]` 是第 k 近的** —— 这是"局部密度"的最好指标。

**注意 `found - 1` 要转 `size_t`**，否则 `int` 下标又会有警告。

### 第 10 段：半径搜索的差异（124-197 行）

半径搜索和 KNN 的结构**完全一样**，只有三处不同：

#### 不同 1：调用的是 `radiusSearch`（151 行）

```cpp
const int found = kdtree.radiusSearch(query, r, indices, sq_distances);
```

**参数是"半径"而不是"个数"。** 返回"实际找到几个"。

#### 不同 2：可能找到很多，要限制显示（154-164 行）

```cpp
const int shown = std::min<int>(found, opt.maxResults);
```

**`shown` 是"打印几个"，`found` 是"找到几个"。**

```cpp
std::cout << "  半径 " << r << "mm 内共 " << found << " 个点";
if (found > opt.maxResults)
{
    std::cout << "（只显示前 " << opt.maxResults << " 个）";
}
```

#### 不同 3：结果按距离排序吗？

**是的，`radiusSearch` 也按距离升序返回。** 所以打印出来的表格
第 1 行一定是最近的。

**（这个"保证升序"是 PCL 的实现细节，不是文档里的 API 承诺。
但在当前版本的 FLANN 实现里确实如此。不要过度依赖它。）**

## 9. 怎么检查结果是否合理

### 检查 1：平方距离 = 真实距离²

第 1 行 `2.1316` 和 `1.4600`：

$$
1.4600^2 = 2.1316 \quad ✓
$$

**每一行都验一遍。如果某一行的平方距离不等于距离的平方，说明打印错了。**

### 检查 2：距离应该单调递增

表格里的"真实距离"列必须是**从小到大**的。如果不是，说明返回结果没排序。

### 检查 3：邻居坐标应该"贴着"查询点

查询点 `(0, 50, 0)` 在管壁上（$\sqrt{0^2 + 50^2 + 0^2} = 50$ = 外半径）。

所以每个邻居的 $\sqrt{y^2 + z^2}$ 应该都接近 50：

| 点 | $\sqrt{y^2+z^2}$ |
|---|---|
| 1: (50.01, 0.12) | 50.010 |
| 2: (50.00, -0.05) | 50.000 |
| 3: (49.88, -1.37) | 49.899 |
| 8: (49.88, 2.63) | 49.950 |

**全在 50 ± 0.1 内** ✓ —— 说明邻居确实是管壁上的点，不是飞点也不是内壁点。

### 检查 4：`18.6%` 的验算

**最远邻居距离是 2.9869**，我第 3.4 节说"最近距离 1.4600 比理论 1.309 大 11.5%"。

**这个 11.5% 是怎么算的**：

$$
\frac{1.4600 - 1.309}{1.309} = 11.53\%
$$

**这个偏差的来源**（第 3.4 节列了 4 条）**不能完全确定** ——
这是一个"合理的解释"，不是"证明"。

**在真实工程里，遇到"数字差 10%"时，正确做法是**：

1. 先确认不是代码 bug（换组参数看趋势是否仍符合）
2. 再给出假设，并**设计一个能验证假设的实验**
3. **不要满足于 "大概是采样相位的问题"**

**本项目没法验证到 1% 精度**，因为噪声本身就有 0.05mm 的随机性。
**但你可以用 `ideal_pipe` 预设（噪声 0.01）重跑一次，看重不重合得好一些** —— 那是你的练习题。

### 检查 5：半径搜索的命中数

半径 5mm 命中 34 个点，第 3.5 节估算 40 个。

**34/40 = 85%** —— 在 15% 误差内，**这个数量级对得上**。

**如果命中数是 3 或 340**，说明搜索逻辑有问题。

## 10. 三个动手练习

### 练习 1（10 分钟）：k 与最远距离的关系

**做什么**：查询点固定 `(0, 50, 0)`，k 依次取 1、2、4、8、16、32。

**填表**：

| k | 最远邻居距离 | $\text{距离}/\sqrt{k}$ |
|---|---|---|
| 1 | | |
| 2 | | |
| 4 | | |
| 8 | 2.9869 | 1.056 |
| 16 | | |
| 32 | | |

**要回答**：最后一列是常数吗？为什么？

<details>
<summary>答案</summary>

**接近常数**（大约 1.0~1.1）。

因为邻居分布在**二维曲面**上。k 个点占据的面积 ∝ k，
而面积 ∝ $r^2$，所以 $r \propto \sqrt{k}$。

**这是"点云是曲面上采样"的直接证据。** 如果点云是**体采样**（填满空间），
那么 k ∝ $r^3$，最后一列会是 $r/k^{1/3}$ ≈ 常数。

</details>

2. **约 38mm**（到内壁）+ 噪声。但注意：管道是**空心**的，轴线到内壁 38mm，

## 12. 与管道焊缝点云处理的联系

### 联系 1：KD-Tree 是焊缝特征提取的"万能工具"

**提取坡口边缘**（张口宽度 b）的典型做法：

```
对每个点：
  1. 用 KD-Tree 找它周围的邻居（半径 3~5mm）
  2. 对邻居做主成分分析（PCA）→ 得到法向
  3. 如果这个点的法向和邻居的"整体法向"差很多 → 这是边缘点
```

**第 1 步用的就是 KD-Tree。**

**没有 KD-Tree，这一步要 O(n²)；有了它，O(n log n)。**

### 联系 2：`k` 的选择 = "看多大范围的局部结构"

**法向估计时**：`k` 通常取 10~30。太小 → 法向被噪声带偏；太大 → 把坡口的棱角抹平。

**这条规律很重要**：**`k` 决定"局部"有多大**。

- `k = 8` → 半径约 3mm → "看得很细，能看见棱角"
- `k = 100` → 半径约 10mm → "看得粗，棱角被当成平滑曲面"

**焊缝坡口的钝边只有 2mm 宽，所以 `k` 必须小（≤ 20）**，
否则钝边的法向会被周围平坦的母材带偏。

### 联系 3：半径搜索的"半径"必须匹配焊缝特征尺度

**在焊接场景里**：

- 找"同一道焊缝上的点"：半径 2~3mm（焊缝宽度 10~20mm 的一半）
- 找"同一个工件的点"：半径 10~20mm（远大于焊缝，小于工件间距）

**这两种需求用的是同一个算法，参数差 10 倍。**

**这就是为什么本项目把"半径"做成菜单参数** —— 让你亲手试出不同尺度的区别。

### 联系 4：真实扫描数据里的"密度不均匀"会直接影响 KD-Tree 的使用

**本项目的点间距处处 1.47mm**，所以"k=20"在任何位置都对应"约 4mm 半径"。

**真实线激光数据**：

- 正对激光处点距 0.5mm → k=20 对应半径 2mm
- 斜射 60° 处点距 3mm → k=20 对应半径 12mm

**同一个 k，在不同位置"看到"的范围差 6 倍。**

**后果**：**基于 k 的邻域（如法向估计）在密度不均匀时会失效**，
必须改成**基于半径的邻域**（半径固定，k 变化）。

**这就是 PCL 里同时提供 `nearestKSearch` 和 `radiusSearch` 的原因。**

## 13. 算法在真实扫描数据中的局限

| 局限 | 说明 | 本项目是否遇到 |
|---|---|---|
| **最坏情况退化到 O(n)** | 点云分布极端时（比如全在一条线上）树退化成链表 | 不遇到（管道是三维分布） |
| **不支持动态更新** | 加点/删点后必须重建树 | 不遇到（读一次查一次） |
| **只支持 float 精度** | `KdTreeFLANN` 内部用 float，距离精度约 $10^{-7}$ | 不遇到（mm 级） |
| **高维失效** | 维度 > 20 时 KD-Tree 比暴力还慢 | 不遇到（3 维） |
| **k 的选择依赖密度** | 密度不均匀时同一 k 对应不同物理尺度 | 不遇到（合成数据均匀） |
| **NaN 存在时行为不确定** | PCL 会跳过 NaN，但 `found` 可能小于 k | 不遇到（无 NaN） |
| **半径搜索的半径也依赖密度** | 半径太小时命中 0 个点 | **会遇到**（练习 2 的空中查询点） |
