# 第一部分：症状索引

## A 类：CMake 配置阶段出错（还没开始编译）

### A1. `CMake Error: The source directory ... does not appear to contain CMakeLists.txt`

**症状**：运行 `cmake -S ... -B ...` 时报这个。

**原因**：`-S` 指向的目录里没有 `CMakeLists.txt`。通常是**当前目录不对**。

**排查**：

```powershell
cd E:\dianyunxulian
Get-Location                    # 确认在项目根目录
Test-Path .\CMakeLists.txt      # 必须是 True
```

**常见错因**：

- 在 `build\` 目录里运行了 `cmake -S . -B .`（`.` 指向 build，那里没有 CMakeLists.txt）
- 拼错了目录名（`E:\dianyunxuliang` 多了一个 g）

**正确做法**：`-S` 永远指向**有 CMakeLists.txt 的那一层**。

---

### A2. `CMake Error: Could not find CMAKE_ROOT`

**原因**：直接双击了 `cmake.exe`，或者 PATH 里的 cmake 坏了。

**排查**：

```powershell
. E:\PointCloudEnv\env.ps1
cmake --version        # 应该输出 4.4.3
```

---

### A3. `By not providing "FindPCL.cmake" ... Could not find a package configuration file provided by "PCL"`

**原因**：CMake 找不到 `PCLConfig.cmake`。

**排查**：

```powershell
. E:\PointCloudEnv\env.ps1
Test-Path E:\PointCloudEnv\PCL\cmake\PCLConfig.cmake     # 必须 True
```

如果 False → PCL 没装在这儿，你需要改 `CMakeLists.txt` 第 34 行：

```cmake
set(PCL_ROOT_DIR "E:/PointCloudEnv/PCL" CACHE PATH "...")
```

如果 True 但还是报错 → 看 `build\CMakeCache.txt` 里 `PCL_DIR` 的值：

```powershell
Select-String -Path .\build\CMakeCache.txt -Pattern "PCL_DIR"
```

**坑**：`CMakeCache.txt` 会**记住上次的值**。如果你改过 `PCL_ROOT_DIR`，
必须**重新配置**（`cmake -S . -B build`）才会生效；如果直接 build，
用的还是缓存里的旧值。**实在不行就删 `build` 重来。**

### A4. `CMake Error: Could not find a package configuration file provided by "VTK"`

**原因**：PCL 的 `PCLConfig.cmake` 会去找 VTK，但没找到。

**排查**：VTK 在 `E:\PointCloudEnv\PCL\3rdParty\VTK`。

```powershell
Test-Path E:\PointCloudEnv\PCL\3rdParty\VTK\lib\cmake\vtk-9.4
```

**注意**：我们的 `CMakeLists.txt` 里 `find_package(PCL ... COMPONENTS ... visualization)` 带上了
`visualization` 组件 —— 这个组件依赖 VTK。**如果你只做算法不做可视化，可以去掉它**，
能省掉 VTK 的一堆依赖。

### A5. `CMake Warning: Manually-specified variables were not used by the project: CMAKE_BUILD_TYPE`

**症状**：配置时警告 `CMAKE_BUILD_TYPE` 未被使用。

**原因**：**这是正常的，不是错误。** 本项目用的是 **Visual Studio 多配置生成器**，
Debug/Release 在**构建时**用 `--config` 指定，不是配置时。

详见 [03_CMake入门.md](03_CMake入门.md) 的「为什么 CMAKE_BUILD_TYPE 无效」。

**你什么都不用做。** 构建时用 `cmake --build build --config Release` 就行。

## B 类：编译阶段出错（C 开头）

编译错误的标准格式是：

```
<文件>(<行号>): error C<编号>: <英文消息>
```

**第一步永远是看最后那句英文。** 它会直接告诉你"什么东西不对"。

### B1. `error C1083: 无法打开包括文件: "pcl/xxx.h": No such file or directory`

**含义**：编译器找不到这个头文件。

**三种原因**（按可能性排序）：

| 原因 | 怎么确认 | 怎么修 |
|---|---|---|
| **头文件名写错了** | 对比 PCL 的 include 目录 | 改拼写 |
| **`target_include_directories` 少了路径** | 看 `CMakeLists.txt` 第 90-93 行 | 加路径 |
| **PCL 根本没装** | `Test-Path E:\PointCloudEnv\PCL\include\pcl-1.15` | 装 PCL |

**验证 include 路径是否真的生效**：

```powershell
Select-String -Path .\build\PointCloudPractice.vcxproj -Pattern "AdditionalIncludeDirectories" | Select-Object -First 3
```

### B2. `error C1189: #error: "Potential runtime error due to aligned malloc mismatch! ..."`

**这是本项目最典型的坑，而且已经解决了，但你要知道为什么。**

**症状**：

```
E:\TOOL\vcpkg\installed\x64-windows\include\pcl\memory.h(69,1): error C1189:
#error: "Potential runtime error due to aligned malloc mismatch! PCL was likely
compiled without AVX support but you enabled AVX for your code ..."
```

**注意报错路径是 `E:\TOOL\vcpkg\...`** —— 但我们用的是 `E:\PointCloudEnv\PCL`！

**原因**：

你的电脑上装了 vcpkg，并且它有**用户级集成**：

```powershell
Test-Path C:\Users\m1445\AppData\Local\vcpkg\vcpkg.user.targets     # 本机 = True
```

这个文件会让 **每一个** VS 工程自动 Import vcpkg 的 targets，
把 `E:\TOOL\vcpkg\installed\x64-windows\include` **塞进 include 路径的最前面**。

于是你 `#include <pcl/point_types.h>` 时，拿到的是 **vcpkg 版 PCL 的头文件**，
但链接的却是 **E:\PointCloudEnv\PCL 版的库** —— 两套版本混用，必炸。

**解决**（本项目 `CMakeLists.txt` 第 29 行已做）：

```cmake
set(CMAKE_VS_GLOBALS "VCPkgLocalAppDataDisabled=true;VcpkgEnabled=false")
```

这行把两个标记写进 `.vcxproj` 的 `<Globals>` 属性组，
让 `vcpkg.user.targets` 里的 Import 条件失效。

**顺带一个好处**：`vcpkg.user.targets` 还会强制 MSBuild 用 `/std:c++17`（2020 之前的规则），
禁掉它之后这个限制也没了。

**验证解决**：

```powershell
Select-String -Path .\build\PointCloudPractice.vcxproj -Pattern "VcpkgEnabled"
# 应该输出 <VcpkgEnabled>false</VcpkgEnabled> 之类
```

### B3. `error C2039: "xxx": 不是 "yyy" 的成员`

**本项目真实案例**：

```
src\main.cpp(24): error C2039: "setupConsole": 不是 "pcp" 的成员
```

**含义**：你调了 `pcp::setupConsole()`，但编译器看不见它的声明。

**原因**：**没有 `#include "core/console.h"`**。

**为什么这个错误很奇怪**：一般函数不存在会说 `C3861: 找不到标识符`。
说 "不是 pcp 的成员" 说明**命名空间 pcp 是存在的**（因为别的头文件里看到了），
只是**这个头文件没被包含**。

**修法**：在调用它的 .cpp 顶部加 include。

---

### B4. `error C3861: "xxx": 找不到标识符`

**含义**：这个名字在编译这一行时**完全没出现过**。

**三种原因**：

| 原因 | 例子 | 修法 |
|---|---|---|
| 没 include | 调 `pcl::io::loadPCDFile` 但没 include `pcl/io/pcd_io.h` | 加 include |
| 没声明 | 函数定义在 .cpp 里但 .h 里忘了声明 | 在 .h 里加声明 |
| **拼写/大小写** | `displayWidth` vs `displayWidthImpl`（本项目真实踩过） | 改对 |

**本项目的真实案例**：我把 `displayWidth` 改名成 `displayWidthImpl` 之后，
`printKV` 里还在调 `displayWidth(...)` → `C3861`。

**教训**：**改名要用 IDE 的重命名功能（F2），不要手动替换。** 手动替换一定会漏。

---

### B5. `error C2664: 无法将参数 N 从 "X" 转换为 "Y"`

**本项目真实案例**：

```
error C2664: "bool pcp::saveCloud(const std::string &, pcl::PointCloud<pcl::PointXYZ>::ConstPtr, std::string &, bool)":
无法将参数 2 从 "pcl::PointCloud<pcl::PointXYZ>" 转换为 "pcl::PointCloud<pcl::PointXYZ>::ConstPtr"
```

**含义**：类型不匹配。

**怎么读这个报错**：

1. 先看**期望的类型**：`ConstPtr`（智能指针）
2. 再看**你给的类型**：`pcl::PointCloud<PointXYZ>`（对象本身）
3. 差了一个 `Ptr` / `ConstPtr`

**修法**：看 `cloud_io.h` 里的声明，传 `result.cloud`（它本身就是 `CloudPtr`），
而不是 `*result.cloud`（那是解引用，得到对象）。

**这个错误的价值**：它逼你**分清"对象"和"指向对象的指针"**，
这是 C++ 最基础也最容易混的一对概念。

---

### B6. `error C2065: "xxx": 未声明的标识符`

**含义**：比 `C3861` 更彻底 —— 连"这是个什么东西"都不知道。

**最常见原因**：**变量名打错，或者变量声明在错误的 `{}` 块里**。

**本项目的例子**：如果在 `if` 块里定义 `double ratio`，在块外面用它 → `C2065`。

**修法**：把声明提到块外面。

---

### B7. `error C2059: 语法错误: "xxx"`

**含义**：纯粹的语法错。

**排查**：看报错行**上一行**是否漏了分号 `;`。
MSVC 的分号错误经常报到**下一行**。

---

### B8. `warning C4819: 该文件包含不能在当前代码页中表示的字符`

**原因**：源文件里有中文，但没告诉编译器用 UTF-8。

**解决**（本项目 `CMakeLists.txt` 第 113 行已加）：

```cmake
add_compile_options(/utf-8)
```

**为什么必须加**：MSVC 默认按系统代码页（简体中文 Windows 是 GBK/936）读源文件，
你存的是 UTF-8，读出来就是乱码，然后 `cout` 输出也乱码，注释里的中文也会让编译器困惑。

**`/utf-8` 一句话解决"源文件编码"和"执行字符集"两个问题。**

## C 类：链接阶段出错（LNK 开头）

**链接错误和编译错误的区别**：

- 编译错误：**某一行代码**有问题（可能拼写、类型）
- 链接错误：**每个文件都编译成功了**，但拼不成一个完整的程序

### C1. `error LNK2019: 无法解析的外部符号 "xxx"，该符号在函数 "yyy" 中被引用`

**这是最常见的链接错误。三个根因：**

#### 根因 1：实现文件没加进构建（最可能）

**症状**：报错说"某某函数无法解析"。

**诊断**：

```powershell
# 1. 函数在哪里定义？
Select-String -Path .\src\**\*.cpp -Pattern "bool pcp::runVoxelGrid"

# 2. 那个 .cpp 在 CMakeLists 的 target_sources 里吗？
Select-String -Path .\CMakeLists.txt -Pattern "voxel_filter.cpp"
```

**如果第 1 步找到、第 2 步空** → 就是它。**加进 `target_sources`，然后重新配置**。

**本项目真实经历**：第一次配置时报 `main.cpp(24): error C2039`，
后来发现 `menu_registry.cpp` 和 `menu_items.cpp` 也忘了加进 `target_sources`
（当时还没到链接阶段，所以没暴露）。

#### 根因 2：声明了但没实现

**症状**：`.h` 里有 `bool foo();`，但没有任何 `.cpp` 写 `bool foo() { ... }`。

**诊断**：

```powershell
Select-String -Path .\src\**\*.h  -Pattern "runXXX"
Select-String -Path .\src\**\*.cpp -Pattern "runXXX"
```

两边数量对不上就是它。

#### 根因 3：命名空间不一致

**症状**：`.cpp` 里写 `void runVoxelGrid() {...}`（忘了 `pcp::`），
但 `.h` 里声明的是 `pcp::runVoxelGrid`。

**这两个是完全不同的函数** —— 一个有 `pcp::` 前缀，一个在全局命名空间。

**C++ 的链接器看的是"修饰名"（mangled name）**，
`pcp::runVoxelGrid` 和 `::runVoxelGrid` 的修饰名不同，所以对不上。

**怎么确认**：看报错里的修饰名。

```
?runVoxelGrid@pcp@@YA?AV?$shared_ptr@...@...  ← 有 @pcp@
?runVoxelGrid@@YA?AV...                        ← 没有
```

**本项目里每个 .cpp 都用 `namespace pcp { ... }` 包住，就是为了避免这个。**

---

### C2. `error LNK2005: "xxx" 已经在 yyy.obj 中定义`

**含义**：**同一个符号被定义了两次。**

**本项目真实存在这种可能性**：如果你不小心把 `console.cpp` 也加进了
`practice/CMakeLists.txt` 之外的某个 target，或者复制粘贴了实现。

**最常见的原因**：**在 .h 里写了函数体，而这个 .h 被多个 .cpp include。**

```cpp
// console.h（错误示范）
void printRule() { std::cout << "----\n"; }   // ← 有函数体！
```

两个 .cpp 都 include 它 → 两个 .obj 里都有 `printRule` 的定义 → `LNK2005`。

**修法**（本项目采用的做法）：

- 声明放 .h：`void printRule();`
- 定义放 .cpp：`void printRule() { ... }`

**如果你确实想在头文件里写实现**，三条路：

```cpp
inline void printRule() { ... }              // 1. 加 inline（最简单）
static void printRule() { ... }              // 2. 加 static（每个文件一份，浪费）
template<typename T> void f() { ... }        // 3. 模板本来就得放头文件
```

### C3. `error LNK1169: 找到一个或多个多重定义的符号`

**这是 `LNK2005` 的伴随错误**，一起出现。修法同上。

### C4. `error LNK2019: 无法解析的外部符号 __imp_xxx`（带 `__imp_`）

**含义**：你调用了某个 **DLL 里的函数**，但没有对应的**导入库（.lib）**。

`__imp_` 前缀是 MSVC 表示"这是从 DLL 导入的"。

**排查**：

```powershell
Select-String -Path .\CMakeLists.txt -Pattern "target_link_libraries"
```

确认 `${PCL_LIBRARIES}` 在。

**更细的排查**：某个组件的 .lib 没链上。比如你用了 `pcl::visualization`，
但 `find_package` 里没写 `visualization` 组件 → `PCL_LIBRARIES` 里没有 `pcl_visualization.lib`。

## D 类：运行阶段出错（程序能启动但行为不对）

### D1. 程序一启动就闪退，退出码 `-1073741515`

**这是本项目第二常见的坑。**

**含义**：

```
-1073741515 (十进制) = 0xC0000135 (十六进制) = STATUS_DLL_NOT_FOUND
```

**"找不到 DLL。"**

**原因**：PCL 依赖 `pcl_common.dll`、`pcl_io.dll`、`vtkCommonCore-9.4.dll` 等几十个 DLL，
它们不在 exe 旁边，也不在 PATH 里。

**排查**：

```powershell
# 1. 检查 exe 旁边有没有 DLL
Get-ChildItem .\build\Release\*.dll | Measure-Object     # 应该几十个

# 2. 检查 PATH 里有没有 PCL
. E:\PointCloudEnv\env.ps1
$env:PATH -split ';' | Select-String "PCL|VTK|Boost"
```

**两种修法**：

**修法 A（推荐，本项目 `CMakeLists.txt` 第 135-195 行已实现）**：
POST_BUILD 自动把 DLL 拷到 exe 旁边。

```powershell
# 验证：改个源文件重新 build，看有没有拷贝日志
cmake --build build --config Release
Get-ChildItem .\build\Release\*.dll | Measure-Object
```

**修法 B（应急）**：每次运行前加载环境。

```powershell
. E:\PointCloudEnv\env.ps1
.\build\Release\PointCloudPractice.exe
```

**注意修法 A 的边界**：它拷的是**直接依赖**。
如果某个 DLL 又依赖别的 DLL（比如 `pcl_io.dll` 依赖 OpenNI2），
那个"间接依赖"可能没被拷 → 还是闪退。

**这就是为什么 `CMakeLists.txt` 里还要单独拷 `OpenNI2.dll`**（第 180-190 行）。

### D3. `[报错] 读取失败（PCL 返回 -1）`

**原因**：文件存在，但 PCL 读不出来。

**三种可能**：

| 原因 | 确认方法 |

**这种文件怎么产生的**：用 `savePCDFile` 保存了一个空点云。

**症状**：控制台显示 `鎴愬姛` 之类的乱码。

**原因**：控制台代码页不是 UTF-8。

**排查**：

```powershell

```

如果是 `936`（GBK）就是这个问题。

**修法**：`setupConsole()` 已经在 `main()` 第一行调用了

**如果还乱码**，可能是：

- 你在**其他函数里输出了中文**，但那些输出发生在 `setupConsole()` 之前？不可能，它在第一行

  这时中文可能变成问号。**重定向时要用 `-Encoding utf8`**

**验证**：

```powershell
.\build\Release\PointCloudPractice.exe
# 直接看屏幕，不要经过管道
```

### D6. 算法跑完，输出"未保存任何文件"

**原因**：看你打印的 `[错误]` 那一行。

**最常见的**：`output/` 目录不存在（程序会自动建，`ensureDir`），
或者磁盘满了。

## E 类：算法结果不对（程序没错，但数字奇怪）

### E1. VoxelGrid 输出点数比输入还多

**不可能**（体素降采样只会减少点数）。如果真遇到 → 你跑的不是 VoxelGrid。

### E2. VoxelGrid 输出点数比预期少很多

**原因**：体素边长设太大了。

**快速估算**：

```
输出点数 ≈ 输入点数 × (体素边长 / 平均点间距)²（对曲面）
```

本项目：平均点间距 1.470 mm，体素 2.0 mm，
理论保留 $(1.470/2.0)^2 = 0.54$，实测 0.59 —— 同一个量级 ✅

**如果体素边长 = 10 mm**：$(1.470/10)^2 = 0.0216$ → 只剩 2% 的点。

### E3. SOR 删掉了太多点

**验收标准**：本项目 200 个飞点，SOR(20, 1.0) 应该删 **196 个左右**。

如果你删了 5000 个：

- `meanK` 太小（比如 5）→ 统计不稳定
- `stdDevMulThresh` 太小（比如 0.3）→ 阈值太紧

### E4. RANSAC 找到的不是平板

**这是本项目最重要的教学点之一。** 详见 [12_RANSAC平面分割.md](12_RANSAC平面分割.md)。

**症状**：内点数约 2213，法向约 `(-0.002, 0.385, 0.923)`。

**原因**：**迭代次数不够**。

平板只占 13.66% 的点，三点都在平板上的概率是 $0.1365^3 = 0.002543$。
1000 次迭代里**一次都没抽中**的概率 ≈ 7.4%。

而圆柱半径 50 很大，管壁在切点附近非常平，**1 mm 的阈值就能把 2213 个点吸成"假平面"**。

**修法**：迭代次数调到 **5000**。

**验收**：内点数 **4131**（正好等于平板点数），法向 `(0, -1, 0)`。

### E5. 欧氏聚类返回 0 簇

**按顺序排查**：

1. **容差是不是小于点间距？**
   本项目周向 1.309 mm、轴向 1.5 mm。容差 1.0 → 0 簇。
2. **`minSize` 是不是太大？**
   设 30000 → 最大簇才 25921 → 0 簇。
3. **`minSize > maxSize`？**
   程序会拒绝执行并提示。

### E6. 欧氏聚类的簇数异常多

**症状**：容差 2.0，得到 20 簇，最大簇只有 12960。

**原因**：**容差刚好卡在斜对角间距的临界点上。**

本项目斜对角距离 $\sqrt{1.309^2 + 1.5^2} = 1.991$ mm，
加上 0.05 mm 噪声，实际距离可能到 2.06 mm。

**容差 2.0 恰好切开了一部分斜对角连接** → 连通图碎裂。

**修法**：容差调到 **3.0**。

**这个案例的教训**：**容差不能刚好等于理论点间距，要留 1.5 倍以上余量。**

### E7. PassThrough 前后点数不对

**验收**：用解析式算一下。

本项目管道半径 50，裁 `z ∈ [-20, 20]`，理论占比：

$$\theta = 2\arcsin\left(\frac{20}{50}\right) = 47.16°$$

$$\text{占比} = \frac{47.16}{360} = 13.1\%$$

但**实测是 27.51%**。为什么？

因为**管子是上半圈和下半圈各有一段** z 落在这个范围内 —— 两段加起来
$2 \times 13.1\% = 26.2\%$，再加上平板的贡献 → 27.51%。

**如果你算出来差得离谱**（比如 5% 或 80%），检查：

- 字段选错了（选了 y 还是 z？）
- 上下限填反了（min > max → 0 点）
- **`negative` 反选了**

### E8. `data\scene_original.pcd` 被改了

**这是最严重的。** 但项目有防护。

**检查哈希**：

```powershell
Get-FileHash .\data\scene_original.pcd -Algorithm MD5
```

**如果变了**：

- `scene_original.pcd.bak` 里有上次生成前的版本，可以改名回去
- 或者直接菜单 1 重新生成（同样的种子 → 同样的数据）

**关于防护**：`saveCloud()` 的第 4 个参数 `allowOriginal` 默认为 `false`，
一旦检测到目标是 `scene_original.pcd` 就**拒绝写入**并报错：

```
[错误] 拒绝写入 scene_original.pcd：原始数据只读，算法结果请写到 output/ 目录
```

**这个保护已实测验证过**（见 [05_编译链接与调试.md](05_编译链接与调试.md) 的第三部分）。

**但注意**：如果你在**资源管理器里手动删除/覆盖**，程序拦不住。
**所以养成习惯：data 目录只读不改。**

## 练习 3（15 分钟）：故意制造 C1083

**步骤**：

1. 备份 `CMakeLists.txt`
2. `target_include_directories` 里删掉 `src`
3. 重新配置 + 构建

**预期**：

```
main.cpp(8): error C1083: 无法打开包括文件: "core/console.h": No such file or directory
```

**修复**：加回去。

**为什么 `src` 这一行很重要**：你的代码写的是 `#include "core/console.h"`，
编译器会去"include 目录列表"里找。`src` 在列表里，才能拼成 `src\core\console.h`。

**如果没有 `src`**：编译器会先在**本文件所在目录**找（`main.cpp` 在 `src\`，所以找 `src\core\console.h` 能找到！），
但 `menu\menu_items.cpp` 也在 `src\menu\`，它找 `src\menu\core\console.h` → **找不到**。

所以你会看到**一部分文件能编过，一部分不行** —— 这正是 `C1083` 有时"只报几个文件"的原因。
